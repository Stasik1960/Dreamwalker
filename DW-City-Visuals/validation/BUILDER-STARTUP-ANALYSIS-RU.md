# Почему DreamWalker долго строит таблицы переходов

## Что показал профиль

Запись `baseline-full/startup.jfr` длится 180 с. Это запуск прежнего DreamWalker v22 RGB Relief BB Half в изолированной клиентской сборке Minecraft 1.20.1 с 51 JAR, Java 17, Fabric Loader 0.18.2 и лимитом heap 6 ГиБ. Первая перезагрузка ресурсов началась на 146,84 с. Событие `CLIENT_STARTED` пришло примерно на 150 с. В исходном отчёте DreamWalker атрибутировано 7 779 из 9 605 Java-сэмплов за фазу старта. [Исходный отчёт](BUILDER-PERFORMANCE-RU.md)

| Разрез полной записи | Сэмплы Java |
|---|---:|
| Все события `jdk.ExecutionSample` со стеком | 11 453 |
| `CompactStateTransitions` в стеке | 7 560 (66,0%) |
| Конструктор, ближайший к вершине кадр этого класса | 4 790 |
| `verifyOwnedMethods`, ближайший к вершине кадр этого класса | 1 857 |
| `get`, ближайший к вершине кадр этого класса | 730 |

Все 7 560 сэмплов этого класса пришлись на `main`. Среди их верхних кадров выделяются конструктор итератора `HashMap` (1 890), `RegularImmutableMap.get` (1 461), `HashMap.TreeNode.find` (974) и `RegularImmutableSet.contains` (758). Эти числа характеризуют горячие операции в Java. Доля сэмплов сама по себе не измеряет долю времени на часах и не прогнозирует выигрыш от правки. В релизном Builder тот же путь подтверждён по байткоду `CompactStateTransitions` и `NewStateStorageMixin`.

## Для чего нужны переходы

Тип блока определяет возможные значения его свойств. `StateManager` создаёт по каноническому `BlockState` на допустимую комбинацию. Например, восемь направлений, два положения створки и два профиля дают 32 комбинации, пока каждое свойство независимо от остальных. Вызов вроде `state.with(OPEN, true)` получает уже созданное состояние с новой створкой и всеми остальными свойствами на прежних значениях. Это нужно при установке и открытии, поворотах, обновлениях соседей и других операциях игры. Таблица строится при регистрации блока и используется для всех его экземпляров на карте. [Fabric Yarn 1.20.1 · State](https://maven.fabricmc.net/docs/yarn-1.20.1%2Bbuild.10/net/minecraft/state/State.html)

DreamWalker уже экономит память. Для своих типов он перехватывает `State.createWithTable`, разделяет описание строк и столбцов между состояниями и хранит ссылки только на значения нужного свойства. Физически плотная таблица резервировала бы для каждой строки все значения из объединения свойств. Компактное представление сохраняет поведение этого интерфейса, включая пустые ячейки.

Сейчас для **каждого** состояния конструктор создаёт изменяемую копию свойств и ищет соседние состояния через `Map<Map<Property<?>, Comparable<?>>, BlockState>`. Он перебирает значения свойств, меняет одно значение во временной карте и ищет результат по её содержимому. Затем выполняет ещё один проход по всем ячейкам логической таблицы, повторяя часть поисков и проверяя доступ по индексам и ключам. Наконец `verifyOwnedMethods` ещё раз проверяет реальные вызовы `with` и `withIfExists`. Эти проверки нужны, чтобы поймать изменение соседей, само состояние и пустые ячейки после подмены стандартной реализации и при взаимодействии с другими оптимизаторами. При большом каталоге повторная работа со свойствами, хеширование и сравнение временных карт оказываются дорогими. В профиле виден обход деревьев бакетов `HashMap`. Его присутствие подтверждает вклад поиска по составным ключам, а точное распределение коллизий требует отдельного счётчика. [Реализация HashMap в OpenJDK 17](https://github.com/openjdk/jdk17u/blob/master/src/java.base/share/classes/java/util/HashMap.java)

## Варианты ускорения DreamWalker

1. **Измерить этапы отдельно.** Добавить счётчики количества состояний и переходов по типам и время построения, обхода всей таблицы и `verifyOwnedMethods`. Это позволит отделить проверки от обязательной работы и найти наиболее дорогие типы.
2. **Убрать повторные проверки из обычного запуска после проверки совместимости.** Перенести исчерпывающий проход по логической таблице и вызовам `with` и `withIfExists` в QA и режим диагностики. В обычном запуске оставить проверки входного домена, наличия канонического состояния и каждого соседа, а также существующий запасной путь для неподдерживаемых схем. Проверить равенство состояний по ссылке, значения текущего свойства, чужие значения, порядок доменов и совместимость с Lithium и ModernFix. Это первая правка для A/B-замера.
3. **Строить переходы через плотный индекс состояний.** На один `StateManager` выделить массив уже созданных состояний. Кодировать комбинацию смешанным основанием по индексам значений свойств. При замене одного значения индекс соседа вычисляется как `index + (newValueIndex - oldValueIndex) * stride`. Так можно заполнить те же компактные таблицы без повторного хеширования карты для каждого соседа. Порядок внутренних индексов можно выбрать отдельно от сохранённых значений свойств, сетевых ID и порядка регистрации. Для неполных, нестандартных или слишком больших доменов нужен текущий путь.
4. **Сокращать количество состояний у новых типов.** Если оформление или служебное значение живёт в `BlockState`, оно умножает остальные комбинации. Перенос свойства в другую структуру может сократить их число, но для существующих блоков потребует миграции карты, сетевого формата и проверки совместимости. Кэш на диске имеет смысл после упрощения алгоритма и при подтверждённом остаточном выигрыше. Он может хранить индексы и подпись схемы. Ссылки на канонические объекты всё равно создаются заново в каждой JVM. Отложенное построение при первом открытии блока может перенести задержку в игру.

## Как сравнивать скорость всей сборки

- Снять по три или более запуска каждого варианта последовательно. Для холодных и повторных запусков считать результаты отдельно. Зафиксировать один JDK, набор модов, настройки памяти, ресурс-паки и шейдеры. Измерять время до конца регистрации, готовности ресурсов и доступного главного меню, затем отдельно время входа на копию Bloodborne.
- После регистрации сравнивать стадии чтения ресурсов, подготовки моделей и загрузки атласа. В записанном наборе уже были Lithium 0.11.4 и ModernFix 5.25.2. Динамическую подготовку ресурсов ModernFix можно сравнить на копии профиля после проверки обоих оформлений, составных моделей и времени появления первого чанка. В профиле записи параметр `mixin.perf.dynamic_resources` оставался по умолчанию. Если проблема в повторной перезагрузке ресурсов, сначала найти её инициатора в логе. [ModernFix для 1.20.1](https://github.com/embeddedt/ModernFix/releases/tag/5.25.2%2B1.20.1)
- Для оценки фризов записать одинаковый маршрут с перемещением, загрузкой новых чанков и поворотами камеры. Сравнить p95, p99 и количество кадров дольше 50, 100 и 250 мс. Сопоставить всплески со сборкой мусора, тиками и подготовкой чанков. Имеющийся замер в семи неподвижных ракурсах после загрузки даёт p95 13,24–15,75 мс для облегчённого профиля. Прогон промежуточной полной сборки до 414,48 с включал вторую перезагрузку ресурсов и параллельные тестовые серверы. Сопоставимой пары прогонов для оценки ускорения пока нет. [Условия предыдущих измерений](BUILDER-PERFORMANCE-RU.md)
