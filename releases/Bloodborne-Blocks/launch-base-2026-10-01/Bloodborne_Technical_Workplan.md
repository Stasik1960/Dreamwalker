## 1. Задача и границы

Получить город для ролевой игры: целые конструкции, исправные проходы, двери, окна и лестницы, понятный каталог предметов, осеннее оформление без очевидных визуальных ошибок. Свободная перестройка всей городской архитектуры игроками не является условием первого запуска.

Работа идёт по типам объектов на всей карте и по конкретным координатам дефектов. Деление на районы, назначение их границ и отдельная перекраска районов не требуются.

Карта rc.4 исключена из кандидатов на основу. Не менять версии Minecraft, Java, Fabric, Yarn и Loom; не выполнять commit, push или запуск production-сервера. Существующие пользовательские изменения рабочего дерева сохранить.

Google Doc «Правки финал» будет использоваться при реализации как источник требований к составу конструкций, самостоятельным деталям, поворотам, состояниям и коллизиям. Конкретные требования документа имеют приоритет над прежними ручными решениями и автоматическим анализом; прямые актуальные уточнения пользователя имеют наивысший приоритет. Текст перечитан 30.09.2026; перед реализацией перечитать актуальную версию. Сейчас изменения мода и карты не выполняются. Предлагаемые ниже отступления от исходных требований остаются предметом уточнения в разделе 3.4 и не считаются одобренными автоматически.

## 3. Уточнения к Google-документу

### 3.1. Один предмет, его состояния и старые идентификаторы

«Один экземпляр конструкции» трактовать как один канонический предмет. Повороты, соединения забора, открытое/закрытое окно и другие необходимые состояния сохранять внутри него. Удалять отдельные предметы-дубли и лишние комбинации, а не необходимые состояния объекта.

Старые registry ID сначала сопоставить с новым предметом и состоянием. Пока в выбранном мире остаются ссылки на старый ID, его нельзя просто удалить: нужна полная замена либо временная совместимая регистрация, скрытая из обычного каталога.

Одинаковая исходная модель может законно использоваться у многих объектов. Запрещать нужно ошибочное двойное владение одним исходным фрагментом в конкретной позиции, а не повторное использование файла модели вообще.

### 3.2. Приоритеты и спорные детали

Порядок решений: прямое актуальное уточнение пользователя → конкретный пункт Google Doc → прежнее ручное утверждение → доказанное совпадение исходной сборки → предложение автоматического анализа. Дата коммита сама по себе не доказывает правильность объекта.

Общее указание документа удалять любые сомнительные блоки предлагаю заменить сохранением до установления принадлежности. Иначе неизвестная часть фасада снова может исчезнуть. Принудительную замену применять к установленному объекту с известным составом; соседство или визуальная похожесть сами по себе недостаточны.

Пункты 3 и общее правило об отдельно встречающихся деталях требуют сохранить самостоятельный предмет там, где деталь действительно используется вне сборки. Например, отдельный кронштейн и тот же кронштейн внутри фонаря не должны создавать конкурирующие правила миграции.

Для пунктов 8, 10, 13, 20 и 21 сначала сопоставить подписи на скриншотах с точными состояниями и прежними галереями, затем сверить несколько полных экземпляров на карте. В пункте 13 соседний исходный блок может содержать и деталь окна, и чужую геометрию: извлечь нужные полигоны, остальное сохранить. Не поглощать соседний блок целиком.

### 3.3. Физика и установка — разные требования

У конструкции отдельно определить: видимую геометрию; препятствие для игрока; объём, запрещающий установку другого объекта; поверхность выбора курсором; служебные клетки хранения.

Общее одноразовое пересечение при импорте и постоянные исключения в пунктах 8, 12, 14, 16 — разные правила. Предлагаемая трактовка:

- Обычные конструкции: разрешить нужное физическое пересечение при подготовке карты; последующая установка предмета при таком пересечении запрещена.
- Пункт 8 и колонна из пункта 16: игрок сталкивается с заданной формой, но эта форма не запрещает установку соседнего объекта. Это постоянное персональное исключение.
- Пункт 14: запрет установки задаёт центральный объём 1×1; внешний объём 3×3×1,5 может препятствовать игроку, но не соседним объектам.
- Пункт 12: отсутствие физической коллизии и запрета установки не означает возможность хранить два самостоятельных Minecraft BlockState в одной клетке. Для совмещения нужна поддерживаемая shared carrier-схема и корректное хранение владельцев.

Формы делать простыми AABB, обрезанными по клеткам. Не округлять все предметы до полного куба: это сломает узкий шпиль из пункта 7, двери и проходимые элементы. Декоративные выступы не расширяют запрет установки, если это прямо не требуется.

Пункт 19 трактовать как приставную climbable-лестницу, а не ступенчатый марш: крепление к стене, отсутствие падения без опоры, возможность наращивания вверх и отсутствие мешающей проходу формы.

### 3.4. Необходимые уточнения

1. Подтвердить описанный приоритет постоянных исключений из пунктов 8, 12, 14, 16 над общим одноразовым разрешением пересечений.
2. Подтвердить замену «удалять сомнительное» на «сохранять до установления принадлежности». Это предотвращает повторную потерю геометрии.
3. Уточнить пункт 22: в прочитанной версии есть только номер, без описания и изображения. Пока не включать его в задания на изменение.

Остальные размеры, варианты и дополнительные детали устанавливать по доступным исходникам и изображениям. Недостающие архивы заново не запрашивать: использовать уже найденное в GitHub и на этом ПК.

### 4.2. Алгоритм для каждого объекта

1. Найти ручное решение и изображение утверждённого результата. Записать идентичность объекта через исходные модели/элементы, состояния и смещения, а не только через старый C-ID.
2. Прочитать соответствующие файлы нужного коммита через `git show <commit>:<path>`. Сохранить необходимые исходники отдельно для сравнения, не выполнять checkout/reset текущего дерева. Из опубликованного JAR извлекать ресурсы как из ZIP, если готовый результат расходится с рецептом.
3. Сравнить старый и текущий объект по составу полигонов и UV, anchor, высоте, поворотам, collision/outline, свойствам open/lit и правилам сопоставления исходных клеток. Выделить именно утраченную правку.
4. Перенести её в актуальный рецепт сборки и согласовать зависимости: текстуры, meshes, contracts, определения, geometry и migration rules. Не копировать готовый большой JSON поверх текущего: он содержит и посторонние объекты.
5. Для старых ID добавить точное соответствие текущим семействам и состояниям. Один исходный экземпляр должен потребляться ровно одним согласованным набором правил; разделение на несколько объектов выполнять одной транзакцией.
6. На небольшом игровом примере подтвердить результат, затем применить то же правило ко всем подходящим экземплярам карты. Утверждённые состав, anchor и состояния закрепить проверкой, чтобы следующая генерация не вернула прежний дефект.

Пример C1491: переносить три группы исходных элементов и три независимых root, а не три копии общей старой модели. Пример C001: сохранить одну полную крону, точные исходные варианты и исправленную ветвь; близость второго дерева не означает включение его частей в первое.

Пример дверей: старое разделение C282 и поздняя полная двухстворчатая дверь описывают разные уровни сборки. Полный подтверждённый шаблон двери имеет приоритет над миграцией одиночного фрагмента; нельзя запускать оба правила на одни клетки. Новые требования Google Doc применяются после идентификации конкретной двери.

## 5. Состав конструкций и автоматизация

Для утверждённого типа хранить в существующих данных ручных решений/рецептах: исходные состояния и модели; смещения относительно anchor; точные номера элементов при разрезании общей модели; исключённый фон/декор соседей; допустимые варианты; итоговые состояния; физические формы и правило установки.

Исходные клетки, видимые полигоны и служебные клетки новой конструкции не считать одним и тем же. Один исходный carrier может показывать части нескольких разных объектов. В таком случае нужна доказанная нарезка полигонов и общий атомарный перенос, а не запрет второго объекта по совпавшей клетке.

Авто-анализ использовать для поиска повторений уже утверждённого шаблона, совпадения формы с учётом поворота и выделения кандидатов на ручную проверку. Сходство имён, общий PNG и касание соседей не являются основаниями для объединения.

Поворотные дубли свести в facing. Соединяемые ограды из пункта 4 свести в один предмет с состояниями прямого участка/угла/соединений; проверить изменение соседей после установки и удаления. Иные каменные опоры не превращать автоматически в выбранную опору без совпадения формы.

Сначала проверить четыре разных случая: целое дерево C001, разделение C1491, окно TEST3 и функциональную дверь. Они проверяют разные ошибки алгоритма до обработки всей карты.

## 6. Подготовка города и однократное пересечение

### 6.1. Выбор исходного мира

Использовать уже найденные ранние полные миры: исходный modded `reference-inputs/latest-modded-world.zip`, опубликованные ранние city-recovery/beta/rc.1–rc.3 варианты и локальные Ether 2.0/2.0.1-lightfix. Выбирать по сохранности реальных конструкций, координатам и совместимости исходных состояний, а не номеру версии.

`reference-inputs/city-recovery-reference.zip` — ограниченный фрагмент, не основа полного города. Миры repair-test/TEST3 — галереи и тестовые примеры, не город. Старый ошибочный original-source и локальные bbmc-карты другой версии нельзя автоматически считать подходящей основой 1.20.1.

Окончательный исходный мир ещё не выбран. Для исчезнувших элементов брать только конкретные проверенные координаты/объекты из подходящих ранних вариантов; не подменять целиком новую локацию старым region-файлом с посторонними изменениями.

### 6.2. Техническая реализация

Опорные модули: `tools/convert_logical_world.py`, `tools/atomic_owner_groups.py`, `tools/build_whole_owner_runtime.py`; runtime — `GeometryRuntime.java`, `ArchitectureBlockItem.java`, `ArchitecturePartBlockEntity.java`.

1. Проверить все используемые состояниями мира registry ID. Для известных старых состояний построить точные mappings; для оставшихся сохранить совместимое представление либо выполнить локальную обоснованную замену. Не загружать полный город новым JAR с неразрешёнными ID.
2. Собрать полные владельческие группы исходных объектов. Преобразование пересекающихся объектов выполнять атомарно: сохранить обе конструкции, их части и привязки.
3. Ввести отдельное разрешение физического пересечения только для offline-подготовки этой карты. Существующий `--conflict-policy aggressive` не считать таким разрешением: он может перезаписывать Bloodborne-состояния, что отличается от сохранения обоих владельцев.
4. Сохранять shared carrier и его владельцев в рамках существующей схемы. `storage_root_geometry()` в `build_whole_owner_runtime.py` поддерживает пустую физически клетку исторического root, но не выбирает новый root и не переносит его. Этот путь подходит для различных root при пересечении их физических объёмов. Два самостоятельных root BlockState в одной мировой клетке так хранить нельзя: настоящий root/root требует нового проверенного разделения storage-root и положения модели либо сохранения поддерживаемого прежнего представления. Не произвольно сдвигать сам объект и не выдавать существующий storage-root фикс за решение всех root/root конфликтов. Чужие block entity и лимит владельцев также не разрешают насильственное затирание.
5. Для персональных исключений добавить явно задаваемый объём запрета установки: предлагаемое новое необязательное `placement_footprint.boxes` в состоянии logical-контракта и соответствующие placement-формы в сгенерированных city/geometry cells. Сейчас такого третьего объёма в runtime нет: есть collision и outline. При отсутствии нового поля использовать существующую collision как стандартный объём запрета. Дополнить загрузчики и `GeometryRuntime` доступом к этому объёму; проверять размеры, преобразования и четыре поворота. Это данные конкретного утверждённого объекта, без жёстко зашитых C-ID в алгоритме и без новой NBT-схемы мира. В обычной установке сравнивать такие объёмы у нового объекта и root/resident/guest-владельцев; совпавшая служебная клетка при непересекающихся формах сама по себе не является физическим конфликтом. Отдельно проверить каждый постоянный тип исключения.
6. Не распространять новую проверку установки на восстановление уже существующих связей при загрузке мира. Старые импортированные пересечения должны пережить сохранение и перезапуск.
7. При разрушении убрать только конкретного владельца и его части; соседнюю конструкцию и общие carriers оставить. Повторная обычная установка пересекающегося объекта должна отказать.
8. Проверить двери и окна при смене open/lit отдельно: новая политика установки не должна случайно запретить взаимодействие с уже существующим объектом. Явно требуемые физические изменения окна из пункта 13 делать в рецепте состояний.

## 7. Как менять внешний вид и готовить варианты

### 7.1. Сначала установить источник нынешней синевы

Сравнить один ракурс с текущими настройками и без шейдера, затем прочитать используемые каменные/кровельные PNG. Разделить цвет материала, освещение и атмосферный фильтр. Глобально повышенная яркость не возвращает утраченные детали тёмной текстуры и может пересветить улицы.

Сохранить композицию и силуэт города. Концепт использовать как направление: более светлый камень, тёмные читаемые крыши, золотая листва, тёплые окна, контраст тёплого света и прохладной тени. Достижение всей детализации концепта не является условием первого запуска.

### 7.2. Материалы вместо замены каждого блока

Построить связи «предмет/состояние → модель или mesh → texture path → UV-область». Для city учитывать `city/meshes.json.gz` и `city/owner-meshes.json.gz`, для logical — `logical/meshes.json.gz` и `visual_models`; разрешать inherited/texture-slot ссылки. Подсчитать использование материалов на выбранной карте.

Сначала менять наиболее заметные и широко используемые поверхности: кладку фасадов, светлый камень деталей, мостовую, крыши, металл, окна и деревья. Так одна проверенная правка материала улучшает много объектов без смены их registry ID.

Общие PNG могут содержать разные материалы. `tree_1.png` и `tree_2.png` — атласы, а не только листва. Для нужных UV-участков создать маски либо отдельные ссылки и текстуры; не заливать весь атлас оранжевым. Там, где одна область используется разными по смыслу деталями, разделить визуальный материал соответствующих полигонов, сохранив игровую геометрию.

Сохранять alpha, UV, размеры и animation metadata. Исправления прозрачности проверить на деревьях, оградах и окнах; не превращать прозрачный фон в непрозрачный прямоугольник. Цвет окон и реальное игровое освещение не считать одним параметром.

После включения выбранного оформления во встроенные ресурсы заново проверить эквивалентность предметов через `tools/build_creative_equivalence.py`. Сейчас эта утилита читает только `src/main/resources`, без внешнего overlay. Для сравнения трёх внешних пакетов сначала добавить проверке чтение эффективных ресурсов «BASE + активный пакет» в отдельной staging-копии либо сохранить видимыми все варианты, которые хотя бы один пакет различает. Старое доказательство совпадения внешности не переносить автоматически: новые материалы могут сделать прежде одинаковые варианты различными. Внешний ресурс-пак сам по себе не пересчитывает статический creative-каталог.

Для деревьев одной перекраски голых ветвей мало. Добавить ограниченное число вариантов крон: золотой, медный, смешанный. Вписать листву в существующий визуальный габарит насколько возможно; сохранить ствол, anchor и утверждённую физику. Не добавлять коллизии каждой веточке или листу. Проверить прозрачные плоскости с четырёх сторон и издали.

### 7.3. Три сопоставимых варианта

| Вариант | Камень и крыши | Осенний акцент | Объём работы |
|---|---|---|---|
| Сдержанная осень | Слегка осветлённый нейтральный камень, сохранённые тёмные крыши | Золото и медь на деревьях, умеренно тёплые окна | Наиболее быстрый |
| Светлая осенняя готика | Тёплый светлый камень `#BFB397`, крыши `#48515C` | Листва `#DDA636`/`#B96A2C`, окна `#FFC56D` | Основной кандидат, ближе к концепту |
| Закатная осень | Более насыщенный тёплый камень, прохладные тени | Янтарные окна, медная листва, усиленная атмосферная теплота | Зависимость от света/шейдера выше |

HEX — начальные ориентиры, окончательные значения подобрать на текстурах и в игре. В третьем варианте теплота материалов должна быть видна и без шейдера.

Сделать три согласованных пакета визуальных замен, включаемых по одному поверх одной и той же сборки. Для city предварительно подтвердить, что выбранные texture/model overrides реально читаются её рендерером; ALT logical не выдавать за такой механизм автоматически.

После разрешения совместимости мира снять шесть фиксированных камер: общий вид, фасад, мостовая с деревом, дверь/окно вблизи, сумерки и ночь. Записать позицию, yaw/pitch, FOV, время, погоду и настройки света. Исходный вид + три варианта дают 24 сопоставимых игровых кадра. Каждый вариант сравнивать с исходником при тех же условиях. Концептуальные картинки не обозначать как скриншоты результата.

### 7.4. Комплект художника

Использовать `tools/export_current_art_bundle.py` и `tools/export_alt_artist_kit.py` как основу. Обновить охват после объединения исправлений; добавить используемые city-объекты и общие материалы, которые текущий ALT-by-block экспорт не охватывает.

Для каждого выбранного объекта дать папку с понятным именем и стабильным ID: собранные виды спереди/сбоку/сзади, BASE_REFERENCE, редактируемые текстуры и модель, UV-развёртку или размеченные UV-участки, контур физической формы для справки, связи с общими PNG и точные пути возврата в ресурс-пак. Материалы с одинаковым runtime path должны получать согласованный результат.

Полигональные модели используют `bloodborne_polygons` с XYZ в блоках и UV 0..16. Прямой импорт этого формата в Blockbench пока не подтверждён. Для удобного просмотра подготовить OBJ/MTL или glTF как производный формат и предварительно проверить XYZ/UV на одном дереве и окне. Экспорт в просмотрщик не является автоматическим обратным импортом. Текстурные правки возвращать через manifest; изменение полигонов — через проверяемое преобразование в штатный формат.

Мою первичную перекраску и варианты крон включить в комплект как редактируемую основу. Художник сможет улучшать выбранный результат, не разбирая заново тысячи технических состояний и не редактируя collision/NBT.

## 8. Порядок работы и критерии завершения

1. Сопоставить пункты Google Doc с конкретными объектами и прежними утверждениями; решить перечисленные смысловые противоречия.
2. Объединить успешные рецепты и проверить четыре опорных случая. Закрепить утрачиваемые исправления в актуальном порядке генерации.
3. Выбрать ранний полный исходный мир, закрыть совместимость ID, пересобрать конструкции с отдельным разрешением импортных пересечений и исправить исчезнувшие части.
4. Параллельно после стабилизации состава объектов подготовить материалы художнику и три варианта оформления. Проверить реальное применение ресурсов logical/city.
5. Применить выбранное оформление ко всем соответствующим материалам города; исправить заметные локальные ошибки по координатам, проверить игровой путь по улицам, дверям, окнам и лестницам.
6. В конце составить галерею объектов на утверждение: все канонические предметы доступного игрокам/администрации каталога, все конструкции Google Doc и восстановленные исправления. Для различных форм и интерактивных состояний дать отдельные образцы; технические rotation/helper-дубли не выдавать за отдельные предметы. Показать итоговый осенний вид, ID и различия вариантов.
7. Собрать единую проверенную сборку и подготовленный город. Публикацию, push и production-запуск этим планом не выполнять.

Проверки после реализации: узкие существующие тесты соответствующих рецептов и миграций; затем из `Bloodborne-Blocks` выполнить `.\gradlew.bat check build logicalGameTest --max-workers=1` на закреплённой Java 17, без изменения зависимостей. Python выбирать по конфигурации рабочего окружения. Добавлять проверки новой логики только на реальные риски, а не на повторение реализации.

Обязательные игровые случаи: whole/split объектов; четыре поворота; угол ограды и удаление соседа; проход через открытые дверь/окно; импорт двух пересекающихся владельцев → сохранение/загрузка → разрушение одного → отказ повторной установки при пересечении → сохранность другого; установка при непересекающихся формах; постоянные исключения документа; отсутствие orphan helpers и исчезновения чужих блоков.

Готовность первого запуска: мир загружается без потери неразрешённых состояний, на доступных игровых путях нет разрывов конструкций и невидимых препятствий, функциональные предметы работают, оформление читается при обычном клиентском освещении, каталог и конечная галерея содержат понятные целые объекты. Дальние декоративные улучшения, дополнительные виды листвы и тонкую атмосферу можно дорабатывать после запуска.
