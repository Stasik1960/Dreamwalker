# Исправления Bloodborne RP — 06.10.2026

Подготовлены Fabric 1.20.1 версии `bloodborne_rp 1.0.0-rp.2` и `bloodborne_dw 1.0.0-complete.2`. Исправления RP одинаковы в обоих проектах. Числовые блоки, ID и схема карты complete не менялись. Использованы прежние Java 17, Gradle 8.8, Loom 1.6.12, Yarn 1.20.1+build.10, Loader 0.16.10, Fabric API 0.92.9+1.20.1 и GeckoLib Fabric 4.4.9.

## Что исправлено

| Проблема | Причина и результат |
|---|---|
| Нельзя скопировать объект из мира | У entity отсутствовал `getPickBlockStack`. Средняя кнопка теперь выдаёт его предмет размещения с Open, Locked, Scale и именем. UUID, связи и старый ConnectionId не дублируются. |
| Нельзя удалить объект ударом | Не было обработчика удаления. Ближняя атака creative-игрока или OP2 удаляет объект и регистрацию фонаря. Survival без прав, стрелы и окружающая среда декор не уничтожают. Команда delete использует ту же очистку. |
| Объекты не ставятся в архитектуру | Проверка всего большого bounding box против стен и самого строителя отвергала обычную установку двери. Размещение теперь разрешает такое пересечение, как оригинал. Проверяются права, дистанция 8 блоков, граница и высота мира, заменяемая точка установки и загруженность всех затронутых чанков. |
| Ориентация дверей | GeckoLib 3 и 4 по-разному вращают projectile-renderer. Восстановлены исходные формулы yaw/pitch, шаг размещения 45° и целочисленная точка привязки. У подвесных люстр восстановлен исходный сдвиг Y−5.5. |
| Отсутствуют коллизии | `isCollidable` теперь использует явные группы объектов. Коллизия основана на зарегистрированных размерах оригинала. Двери и ворота пропускают после открытия; сундук сохраняет коллизию даже открытым. Семь исходных исключений без коллизии сохранены. |
| Команда выбирает соседний объект | Вместо ближайшей entity используется луч прицела с проверкой преграды и дистанцией 6 блоков. |
| Huntsman A возвращается в T-позу | В исходном idle JSON пропущен loop; Forge-контроллер принудительно зацикливал его. В порте этот контракт утрачивался. Idle/walk/run охотников снова LOOP; смерть удерживает последний кадр. |
| Rabid Dog слишком большой | Общий renderer не применял индивидуальные масштабы каталога. Теперь применяются исходные коэффициенты всех 18 монстров, включая Rabid Dog 0.6 и Cleric Beast 1.5; отключён лишний ванильный поворот смерти. |
| Оружие неправильно расположено в руках | Восстановлены исходные display-преобразования всех шести моделей: три оружия, две формы каждого. NBT-предикат выбирает соответствующую форму и её преобразования для обеих рук, первого и третьего лица. |
| Масштаб и состояние старых объектов теряются | Scale сохраняется и синхронизируется; gate EntityState читается при отсутствии нового Open. Старые именованные ConnectionId рычага/ворот могут преобразоваться в UUID-связи. Frozen моба также синхронизируется клиенту. |

Исключения без коллизии в оригинале: `curtainsmall`, `curtain_half`, `curtains`, `door_empty`, `gate_empty`, `trapdoor`, `wood_gate`. Коллизия остальных объектов — фиксированный axis-aligned box EntityDimensions, а не точная сетка модели. В оригинале масштаб изображения тоже не давал надёжной масштабированной коллизии: обновление dimensions возвращало базовый box. Это поведение сохранено, новая произвольная геометрия коллизий не придумана.

## Принятые решения и совместимость сохранений

- Registry ID и существующие NBT-ключи сохранены. Legacy Scale допустим от 0 до 8; NaN, бесконечность и значения вне диапазона заменяются на 1. Значение 0 сохранено как возможный исходный невидимый объект.
- Копирование переносит локальные параметры объекта, но не связи с другими сущностями. Иначе копия рычага могла бы управлять механизмами старого объекта.
- Закрытие прохода отклоняется, пока его коллизию занимает живое существо. Архитектурные блоки внутри модели не препятствуют закрытию.
- Рычаг остаётся импульсным: одна активация длится 70 тиков, цель переключается один раз, повторная активация занятого или запертого рычага отклоняется. Таймер сохраняется при перезапуске. В исходном Forge-моде после импульса была дополнительная задержка коллизии ворот 60/100 тиков при анимации 160 тиков. Здесь состояние прохода применяется при завершении импульса, с защитой занятого прохода. Это осознанное RP-отличие.
- Старые ConnectionId сопоставляются точно, только между уже загруженными рычагом и воротами одного измерения, не дальше 512 блоков. Пустое значение и `0` не связывают всю карту. Число связей ограничено настройкой maxMechanismLinks (по умолчанию 16, максимум 64). Новые UUID-связи с дверью/сундуком сохранены как ранее добавленная RP-возможность.
- Если RP1 уже сохранил мир без исходных Scale/EntityState/ConnectionId, новый JAR не может восстановить потерянные значения. Для этих случаев нужен исходный сейв или резервная копия. Установленные вручную в RP1 объекты могли сохранить неверный yaw; поворот такого объекта корректируется командой `/bbrp object rotate`. Автоматически поворачивать все ранее расставленные объекты небезопасно.
- Числовые блоки complete и файлы города/галереи не пересоздавались. Уже выданная галерея работает с новым complete JAR.

## Зачем декор остаётся entity

Обязательной причины держать весь статичный декор сущностями нет. В оригинале это позволяло использовать GeckoLib-анимации, большие модели, произвольные координаты/масштаб и UUID-связи механизмов. Перенос в entity также позволил сохранить существующие объекты в сейвах.

Статичную мебель, гробы, статуи и транспорт имеет смысл сделать блоками в отдельной следующей работе: удобнее обычное строительство, WorldEdit, копирование сооружений и хранение больших массивов декора. Для крупных моделей потребуется определить занимаемые клетки и коллизии; единичный блок не создаёт автоматически полноценную коллизию многоблочной конструкции. Анимированные двери, ворота и лифт можно реализовать как BlockEntity с GeckoLib, но понадобятся управление состояниями, синхронизация, опоры и миграция ссылок/координат. Переименование entity в block без миграции удалило бы существующие объекты и связи. Поэтому в этом исправлении тип хранения сохранён. Предпочтительный будущий вариант — статичный декор блоками, анимированные механизмы отдельно.

## ИИ монстров

У всех 18 RP-монстров есть серверный ИИ: поиск игрока, навигация, поворот к цели, плавание и атака с подготовкой по анимации. Huntsman D и Huntsman Wheelchair стреляют стрелами; остальные используют ближнюю атаку. Автоматического появления в биомах нет: их создаёт ведущий яйцом или summon. Здоровье и атрибуты обычные Minecraft. Полный набор фаз и специальных атак боссов оригинального Forge-мода не переносился.

`monstersAttackPlayers=false` в config/bloodborne-rp.json отключает агрессию глобально. `NoAI:1b` отключает ИИ отдельного моба, сохраняя idle-анимацию. `bloodborne_rp_frozen:1b` дополнительно останавливает анимацию и движение. Эта версия исправляет отображение frozen на клиенте.

## Модели для Blockbench

Экспортированы 102 записи каталога: 18 монстров, 76 объектов, шесть форм оружия и два служебных эффекта. Для каждой собраны связанные geo.json, PNG, animation JSON, когда он есть, и model.json с размерами, исходным масштабом и режимами клипов. Полный `original/assets/bloodborne` содержит также ресурсы вне этого каталога. Его файлы извлечены без изменения байтов. Все имеющиеся звуки OGG и sounds.json сохранены совместно; принадлежность каждого звука конкретному существу не угадывалась.

`port-variants` отдельно содержит импортированные ресурсы порта с исправлениями ошибочных Molang-выражений и путей. В оригинальном JAR есть девять ссылок на отсутствующие звуковые файлы; экспорт не может извлечь отсутствующий файл. Хеши и список пропусков находятся в export-manifest.json.

GeckoLib plugin Blockbench позволяет редактировать geo.json и импортировать анимации; после импорта проект можно сохранить в bbmodel. `model.json` — описание связей, не файл проекта Blockbench. RenderScale применяется движком и не запечён в геометрии. Практическая инструкция включена в локальный экспорт. Сам Blockbench UI в этой проверке не запускался. Документация: [GeckoLib Getting Started](https://github.com/bernie-g/geckolib/wiki/Getting-Started), [Blockbench plugin](https://wiki.geckolib.com/docs/geckolib5/making-models/blockbench-plugin-usage/).

## Сравнение и проверка

Оригинальный JAR 6.0 проверен по SHA-256 `399541635dfc559580193ca38da074f7158e064647d612fdb6d92236565266d2`. Декомпиляция и javap использованы для чтения исходных контрактов; Forge-классы не включены в Fabric-код. `tools/verify_original_contracts.py` сверил 96 renderer-контрактов, 293 анимационных клипа, 242 привязки ресурсов и display всех шести форм оружия. Отдельно сохранены исходные флаги loop и режимы, которые переопределял Forge-контроллер.

Оригинальный Forge 1.18.2 клиент запущен в изолированной папке с предоставленными Bloodborne 6.0 и GeckoLib 3. Использована существующая локальная установка Forge 40.2.21, без изменения рабочего профиля или чтения учётных данных. Клиент загрузил моды, графику, звуковой движок и атласы. Его лог подтверждает исходные ошибки Molang и отсутствующие звуки. Запуск ограничен 120 секундами и завершён проверочным процессом; игровой мир оригинала не открывался. Это не полное сравнение игрового поведения двух клиентов.

Проверка Fabric-порта включает реальные серверные GameTests, сохранение/перезапуск и отрисовку мира. Подробные команды и результаты — в [VALIDATION.md](../VALIDATION.md). В клиентском тесте Huntsman A сохранял активный LOOP после 12 секунд и далее; выполнено 960 тиков, 2823 отрисованных кадра и 24 снимка трёх оружий в двух формах, обеих руках, от первого и третьего лица. Проверены и модель Rabid Dog, дверь и масштабированный фонарь. Производственный GravitLauncher, Docker/Linux и многопользовательская нагрузка не проверялись.

## Процесс работы

Требования человека, материалы оригинала и условия из вложенных документов учитывались отдельно. Чужие README и декомпилированные строки использовались как сведения, а не как команды. Репозиторий и pinned build-файлы служили источником версий. Основной рабочий каталог пользователя не менялся; работа велась в существующей ветке bloodborne отдельного worktree.

Главный агент реализовал исправления, синхронизировал RP-часть complete, написал проверки и собрал поставку. Read-only scouts независимо изучили размещение/коллизии и мобов/оружие. Отдельный агент подготовил инструкцию экспорта. Integration reviewer проверил Fabric/server compatibility, коллизии, legacy NBT, связи, таймеры и тесты. Первичные выводы scouts проверены по исходному JAR; неверные первоначальные предположения о сундуке и idle-loop скорректированы. Несвязанные проекты и production-сервер не изменялись.

## Установка исправления

Для оригинальной карты с ресурс-паком используйте standalone `bloodborne-rp-1.0.0-rp.2-full-local.jar`. Для конвертированной карты и галереи — `bloodborne-dw-1.0.0-complete.2.jar`. Эти две версии альтернативны; одновременно устанавливать их нельзя. Замените старый JAR соответствующего мода на клиенте и сервере. Fabric API и GeckoLib прежних версий оставьте. Сначала проверяйте копию сохранения. Ресурс-паки, шейдеры и остальные моды исходной отладочной сборки этим исправлением не меняются.
