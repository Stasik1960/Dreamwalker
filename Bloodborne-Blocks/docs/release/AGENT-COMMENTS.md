# Комментарии агента к задаче production-релиза

## Продолжение production-задачи: 2.1.0-rc.1, 2026-09-27

Runtime выбран из `b086e8892`; repair не переносился. Исправлены две причины
невоспроизводимого CI: shallow checkout не содержал историческую базу grid-check,
а Python зависимости не включали Pillow. Теперь история полная, NumPy/Pillow
зафиксированы. Локальные check/build/package и 37 GameTests прошли; подробности
текущего запуска — в [RELEASE-STATUS.md](../RELEASE-STATUS.md).

По разрешённому пользователем варианту выбран новый JAR `2.1.0-rc.1`:
эквивалентность пяти отличающихся beta.3 class-файлов не заявляется. Старые
сравнения сохранены как исторические, не как доказательство нового пакета.

Главный вывод независимого review: прежний recovery устраняет счётчик missing
за счёт возврата к предыдущей раскладке, а не восстановления текущих transient
composite assets. Plan заменяет 30 неизвестных клеток helpers и 3 — воздухом.
Это противоречит нынешнему требованию сохранить неизвестное без перезаписи.
Нули старого recovery verifier подтверждают принятую политику замены, а не
сохранение утраченной геометрии/коллизий. Поэтому прежнее предположение, что
recovery закрывает текущий missing-input blocker, отвергнуто.

Единственный непосредственный blocker — authoritative model/composition data
для 23 ID / 33 клеток; exact input и минимальный шаг указаны в status. После
его обнаружения compatibility/conversion/runtime работы остановлены согласно
заданию. Мир, repair WIP и `main` не изменены. Остальные production-проверки
остаются непроведёнными и должны быть выполнены после поступления данных.

## В чём проблема

Мод собирается и проходит текущие проверки. Однако способность собрать JAR и
поставить несколько тестовых объектов не доказывает, что обновление правильно
прочитает старый город, сохранит многоблочные объекты и переживёт перезапуск.
До этих доказательств называть сборку production-релизом было бы преждевременно.

У проекта две разные линии разработки. `main` находится на beta.3 и совпадает
с архивной веткой, названной `beta3-grid-fragmentation-broken`. Repair-линия
содержит TEST3 и дальнейшую локальную работу над целыми объектами. Её результаты
не попадают в `main` только от того, что сохранены на этом же компьютере.
Поэтому числа 37, 56 и 57 GameTests относятся к разным наборам и исходникам;
это не изменение количества успешных тестов одного неизменного релиза.

Важное различие — корректность клетки и сохранность объекта. Конвертер может
присвоить каждой клетке существующий ID и получить чистый registry census.
Но дверь, окно или другой составной объект всё ещё может потерять связь между
частями, область взаимодействия или владение helper-клетками. Поклеточный
fallback в `main` не доказывает сохранение этих отношений для всего города.

Старые registry IDs и ItemStack требуют отдельной совместимости. Пустые
`rules`/`item_aliases` и успешные тесты текущих IDs не дают такого доказательства.
Из этого не следует, что каждый старый объект обязательно потеряется; следует,
что безопасный upgrade path пока не подтверждён.

## Что установлено, а что остаётся неизвестным

| Наблюдение | Мой вывод | Чего оно не доказывает |
|---|---|---|
| Свежие check/build и 37 GameTests прошли | Текущий набор code/data/geometry/contracts работает в проверенном окружении | Полный город, графику и production restart |
| TEST3 содержит старую цифру 6518 protected failures | TEST3 не закрывал полный городской gate | Что 6518 — результат нового прогона `main` |
| Отдельная локальная repair-диагностика дала 1979 неполных protected-объектов | В этой диагностике остаются реальные незакрытые случаи | Что эти исправления перенесены в `main` или что два числа можно напрямую вычитать |
| 355/356 объясняются strict/shared-binding и прежним scalar checker | Есть объяснение различия методик | Точный one-group delta: полных первичных payload для него нет |
| В опубликованном и локальном JAR отличаются пять классов | Полная воспроизводимость этого старого артефакта не доказана | Что найдена ошибка gameplay, повреждение JAR или подмена |
| Клиентский QA, restart и performance не выполнены | Соответствующие gates остаются открытыми | Их успех из результатов GameTests |

Для class-file различий вероятны эффекты компиляции/ремаппинга: большая часть
сырого diff относится к constant-pool индексам, offsets и debug tables. Это
**гипотеза**, а не закрытие blocker: остаточные opcode-различия требуют отдельного
семантического сравнения и восстановления точной сборочной среды.

16 исторических Python failures/errors, воспроизведённых на прежней базе, тоже
нельзя считать исправленными только потому, что они исключены из текущего
Gradle `check`. Для production-совместимости нужно определить их актуальные
контракты, восстановить соответствующие fixtures и получить проверенный результат.

## Что дала последняя задача

Подготовлена проверяемая база для следующего инженерного шага: разделены ветки
и источники результатов, согласована версия, сохранены старые документы,
добавлены scoped release gates, проверки package/version/SHA и Bloodborne CI.
Независимый review нашёл и помог закрыть ошибки в самих новых валидаторах и CI;
финальные 16 gate-тестов и 4 package-теста прошли.

При этом первоначальная цель «готовый production-релиз» **не достигнута**.
Оптимизация registry, новая конвертация, устранение оставшихся городских
ошибок и реальный клиентский QA не выполнялись. Runtime Java и ресурсы `main`
не менялись. CI подготовлен как инфраструктура проверок; это не завершение
фазы runtime QA и не разрешение выпуска.

Манифесты source/resources относятся к фактически проверенной Windows-копии
и учитывают её окончания строк. Они не заменяют Git commit и не обещают тот же
байтовый SHA после другого checkout. Для новой сборки нужен новый связанный
набор source/resource/artifact fingerprints. Опубликованное evidence сохраняется
без преобразования его байтов Git.

## Рекомендуемый следующий шаг

1. Закрыть оставшиеся provenance-вопросы и зафиксировать выбранную базу.
   Отдельно решить судьбу repair-линии; автоматический merge здесь не обоснован.
2. На небольших точных fixtures доказать legacy chunk/ItemStack compatibility
   и сохранность целого owner-графа. Для каждого типа отказа иметь пример до,
   ожидаемый результат, отказ при конфликте и повторное чтение после save/restart.
3. Затем подготовить read-only план по фиксированному MODDED-входу: owners,
   physical/interaction footprints, чужие блоки, неизвестные IDs, helpers и
   целые транзакции. Не ослаблять guards ради уменьшения числа rejected groups.
4. Только после этого отдельно разрешать полный проход на копии, независимую
   проверку и повторный проход. Для неизвестных данных нужны доказательства
   сохранения или явный BLOCKED; подмена воздухом недопустима.
5. После совместимости мира выполнить dedicated/client QA и измерить startup,
   память, reload, FPS/TPS на фиксированной конфигурации. Оптимизацию оценивать
   по этим измерениям, а не по сокращению элементов creative tab.

Публикуемая audit-ветка содержит эти выводы и инфраструктуру проверки.
Она не является новой игровой версией и не переносит локальный repair runtime в `main`.
