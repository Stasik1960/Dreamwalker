## 2. Окно должно находиться ПЕРЕД стеной, а не делить с ней клетку

Пользовательские симптомы:
- окно визуально частично утоплено в стене;
- обычную лаймовую шерсть и другие полные блоки нельзя поставить позади во всех нужных местах, хотя специальную кирпичную ограду можно;
- снизу виден нежелательный отступ/зазор;
- требуется обычное настенное размещение без специального объединения окна с материалом стены.

Шесть скриншотов показывают результат теста. Изображения не задают точное численное смещение. Вычисли его по текущей модели, её раме/подоконнику, anchor и transform, а не по перспективе картинки.

### Целевая пространственная схема

`[обычный блок стены] | плоскость её грани | [тонкое окно в соседнем столбце клеток]`

Важное ограничение: это НЕ разрешение помещать второй vanilla BlockState в те же координаты, что и окно. Стена и окно должны иметь разные реально занимаемые клетки.

- Окно остаётся одним цельным объектом и одним предметом, с существующими ставнями, открыванием, BASE/ALT и поворотами.
- Для обычного размещения окно использует свой столбец 1×2 клетки ПЕРЕД стеной: root и верхняя helper-клетка. Не расширяй эту маску из-за декоративной геометрии или открытых ставней.
- Модель расположена у задней границы этого переднего столбца, вплотную к наружной грани стены, а не посередине стены и не с воздушным зазором.
- Физика и выделение согласованы с новым размещением. Collision остаётся тонкой и cell-local, в пределах собственных физических клеток окна. Не превращай её в два полных куба и не убирай полностью.
- Все клетки стены позади, а также не занятые окном боковые клетки остаются обычными клетками: их можно устанавливать, удалять и заменять независимо от окна. Не вводи новое автоматическое удаление окна при изменении его задника.
- Направление монтажа определяется гранью стены, по которой нажал игрок; проверь все четыре горизонтальные стороны. При отдельной установке на площадке сохрани понятный существующий способ выбора facing и ту же геометрию.
- Не делай сплошную стену прозрачной, не вырезай её и не заменяй другим типом. Если пользователь хочет видеть через окно, он сам оставляет проём. Сплошной блок за рамой закономерно остаётся видимым.

### Вертикальное положение

Убери внутренний вертикальный отступ самого окна: нижняя опорная кромка подоконника должна совпадать с согласованной опорной плоскостью при установке на полный блок.
Используй фиксированное, измеренное по модели локальное смещение, одинаково применимое к нужным состояниям. Не вычисляй высоту на лету по ближайшей ограде и не растягивай её модель, чтобы закрыть зазор.
Неполный блок может иметь собственную меньшую высоту — не обещай контакт с любой такой поверхностью через деформацию окна.

Пользователь разрешает именно эти изменения позиции окна: наружу к грани стены и вниз до корректной опорной плоскости. Не меняй его масштаб, UV, текстуры, состав частей или дизайн. Сдвигай согласованно render/selection/collision и при необходимости локальный anchor; не «чини» только картинку при оставленной в стене физике.
Сохрани согласованность ручной установки и будущего размещения конвертером. Не делай сейчас массового перемещения объектов в городе.

### Чего НЕ делать

Не расширяй shared ownership на vanilla/сторонние блоки. Не добавляй им BlockEntity, mixin, специальную регистрацию или исключения по материалу. Не делай helpers глобально заменяемыми.
Не создавай окно, автоматически заимствующее текстуру стены; не вводи систему вырезания проёма или динамического совмещения моделей.
Существующий shared-runtime и исправленную кирпичную ограду не удаляй: они уже работают в других сценариях. Но для обычного навешивания этого окна они не должны быть необходимы.

Пользователь не требует убирать уже существующие красивые соединения ограды, только запрещает далее усложнять контакты ради этой задачи. Не добавляй новую специальную связь «окно = секция ограды».

## 3. Все размещаемые блоки — во вкладку мода

Текущий фильтр креатива скрывает большую часть зарегистрированных архитектурных блоков. Сделай их доступными без команд и поиска образца на карте.

- В существующей вкладке Bloodborne должны быть все зарегистрированные размещаемые блоки мода с BlockItem: production logical, новые строительные типы, цельные исторические `owner_*`, прежние/native compatibility и `city_*` с предметами.
- Начало списка: нормальные цельные/строительные блоки. Ниже: совместимость/технические секции, явно помеченные как таковые в названиях или подсказках. Не выдавай их за нормализованную строительную палитру.
- Не скрывай реальные зарегистрированные ID только потому, что их обычный pick/drop перенаправлен на новый строительный предмет. Не меняй существующие pick/drop/placement правила ради оформления меню.
- Для контейнеров `city_*` перечисли доступные визуальные `variant`, а не только `variant=0`. Используй существующие ItemStack/BlockStateTag и модели, не регистрируй новый блок на каждый вариант.
- Для обычных объектов покажи доступные художественные варианты и BASE/ALT через поддерживаемые item-state данные. Не перечисляй декартово произведение facing/open/lit/соединений и служебных anchor-состояний: это не отдельные строительные предметы.
- Не создавай предмет для `architecture_part` и иных служебных блоков без самостоятельного размещения. Это не пользовательская модель; укажи такие исключения в отчёте.
- Не создавай новые независимые фрагменты и не меняй группировку моделей. Доступ в меню не означает, что техническая секция стала цельным объектом.
- Не делай сложный новый каталог/GUI. Используй существующую вкладку, устойчивый порядок и обычные подсказки. Списки строятся при заполнении вкладки, без тикового обхода мира и генерации новых meshes.

Добавь проверку покрытия: каждое допустимое BlockItem/визуальное значение представлено либо имеет конкретную причину исключения. Итоговые числа получи из реестра, не захардкоживай.

## 4. Короткая реальная проверка, а не новый большой forensic-проход

Сначала воспроизведи нынешнее размещение окна, затем проверь исправление на существующем малом тестовом мире.
Новый стенд должен использовать обычные `minecraft:lime_wool`, stone/brick, planks и glass, а не только специальный SharedArchitectureBlock.

Обязательные сценарии с настоящим использованием предметов:
1. Построить сплошную стену → повесить окно на её грань; все четыре направления.
2. Поставить окно → заполнить обычными блоками задний столбец по всей высоте окна, сверху и снизу; не заполнять собственные клетки окна.
3. Удалить/вернуть блоки задника и снять/вернуть окно; другой объект и предмет в руке не теряются, foreign blocks не перезаписываются.
4. Открыть/закрыть ставни рядом со сплошной стеной: окно не смещается, задник не меняется, новые helpers в стене не появляются.
5. Проверить положение неподвижной рамы/подоконника относительно грани стены и полного опорного блока; все facing, BASE/ALT и open-состояния.
6. Проверить целое разрушение окна и отсутствие orphan helpers. Проверить сохранение NBT; фактический перезапуск клиента не объявлять пройденным без запуска клиента.
7. Открыть вкладку, взять предметы из всех её разделов, проверить несколько ненулевых city-вариантов и вариант дерева: после установки должен получаться выбранный вариант.
8. Повторно прогнать прежние регрессионные тесты C001/C474/C618, ограды и общих клеток, если затронут общий runtime.

Не подменяй проверку размещения прямым `world.setBlockState` в тестируемом действии. Он допустим для подготовки стенда.
Не проверяй только Boolean facing: проверь результирующий transform и физические клетки.

Если локальный фикс подтверждён, выполни сборку и существующие необходимые тесты. Не повторяй полный многомиллионный обход города после каждого маленького изменения.
