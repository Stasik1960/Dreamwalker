## Окно: измерение и граница разрешённых изменений

Для NORTH предмет уже выбирает соседнюю клетку перед нажатой гранью стены.
Корень окна находится в переднем столбце, стена — при локальном `z=1..2`.
В TEST2 неподвижная рама заканчивается при `z=.25`, нижняя кромка подоконника
находится при `y=-.875`, итоговый `render_offset=[0,0,0]`. Физика занимает
ровно root и root+UP, но тонкая плоскость находится при `z=0.. .125`.

Для контакта рамы с задней границей собственной клетки нужен одинаковый
сдвиг `-.75 * facing` по горизонтали. Контакт нижней кромки с верхом полного
блока непосредственно под root требует `+.875` по Y. Это нормализация
относительно корня; буквальное опускание на `.125` увело бы подоконник на
`y=-1`, внутрь опорного блока. Изменять целочисленные root/anchor не требуется.
Тонкая физика переносится к задней границе клетки (`z=.875..1` для NORTH),
маска владения остаётся 1×2. Selection следует полному визуальному контуру.

Отдельно обнаружено противоречие исходной открытой позы с прилеганием к
сплошной стене: её сырая граница `maxZ=.620764`; после сдвига рамы к стене
`maxZ=1.370764`. Следовательно, прежняя поза открытых ставней пересекает
задник на `.370764` блока. Сдвигать только открытое состояние целиком нельзя:
сместится и неподвижная рама. Для устранения этого пересечения требуется
отдельное разрешение изменить направление раскрытия створок при сохранении
их формы/UV/текстур; уточнение отправлено пользователю. До решения это
**открытый блокер выпуска**, а не пройденная визуальная проверка.
Авторские элементы 0/1 — створки, 2/3 — подоконник/рама. Одного изменения
знака нынешних ±22.5° недостаточно; найденный вариант коррекции меняет только
поворот двух створок до 90°. Он ещё не применялся.

Исходные meshes пока не изменялись. Общий shared-runtime, IDs, формат NBT,
правила ограды и конвертер не менялись.

## Вкладка

Список строится из зарегистрированных BlockItem при заполнении существующей
вкладки. Порядок: production/строительные, исторические цельные owner,
native compatibility, технические city-секции. Подсказки поясняют назначение.
Перенаправление pick/drop больше не скрывает зарегистрированный предмет.

Перечисляются художественные `variant` и `visual=base/alt`; повороты,
открывание, свет, соединения и служебные anchor-состояния не размножают список.
Значения, которые существующая placement policy принудительно заменяет,
фиксируются как исключения. `architecture_part` не получает предмета.
Модель предмета использует выбранные художественные значения и уже испечённые
модели; дополнительные meshes при открытии вкладки не генерируются.

Проверка покрытия сравнивает фактическую вкладку с реестром и StateManager,
а не с жёстко заданным числом. Отдельные GameTests устанавливают предметы из
каждого раздела, небазовый вариант дерева ALT и ненулевые city-варианты.
Результат: все **3827 BlockItem**, **46669 записей**. По разделам: 139
production/строительных вариантов, 863 исторических цельных owner, 49 native
compatibility, 45618 city-вариантов. Пропусков нет. Конкретные исключения:
`architecture_part` не имеет BlockItem; `o_c654_a.variant=source_depth`
принудительно заменяется существующей политикой размещения на `surface`.

ожидающий решения по позе ставней; это не опубликованный окончательный TEST3.

на временной копии. Маски остальных семейств целиком сверяются с TEST2.
GameTests не доказывают отсутствие клиппинга открытых створок: их текущая

- 355 из 3238 атомарных групп проходят; оставшиеся 2883 требуют работы/проверки.

- Это пересекающиеся счётчики разных сущностей; их нельзя складывать или
  называть числом уникальных моделей.
- Надёжного общего числа уникальных семейств с runtime-багами из этих
  отчётов не следует. В текущем узком воспроизведении проблемное семейство
  одно: `o_shuttered_window`; это не аудит всего каталога.

этап после пользовательской приёмки — копия неизменяемого MODDED-бэкапа,
существующий атомарный конвертер, один новый полный проход и анализ остатка.
