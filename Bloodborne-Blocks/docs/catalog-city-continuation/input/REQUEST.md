ОСТАВШАЯСЯ ЛОКАЛЬНАЯ ЗАДАЧА: КАТАЛОГ И GUI

1. Убрать повторы из обеих вкладок.
   В основной вкладке: один подтверждённый строительный тип / один реально
   отличающийся художественный вариант — одна запись.

   Повороты, open/lit/connection/root_anchor уже не размножают каталог:
   не трать время на повторную реализацию сделанного.

   Проверь оставшиеся художественные варианты, BASE/ALT и aliases.
   Когда они дают одинаковую установленную модель, материалы и поведение,
   показывай один канонический представитель.
   Если BASE и ALT сейчас одинаковы, скрывай повторную запись, но сохраняй
   оба состояния и возможность будущего альтернативного оформления.

   Используй существующие mappings и фактические разрешённые модели/текстуры.
   Разные пути к одинаковому содержимому не доказывают различие.
   Одинаковое название или похожая миниатюра не доказывают эквивалентность.
   Не объединяй функционально разные блоки по одному внешнему сходству.

   Для технической вкладки можно агрегировать доказанные эквиваленты,
   сохранив список исходных ID/state в отчёте. Не создавать новый registry
   ради красивого меню и не начинать глобальный semantic discovery.

2. Исправить слишком большие иконки предметов.
   На пользовательском скриншоте модели вылезают за границы слотов
   и перекрывают соседние предметы.

   Центрировать и вписывать каждую выбранную модель в стандартный GUI-слот
   с небольшим отступом, сохраняя пропорции.
   Менять ТОЛЬКО GUI-представление.
   Не менять масштаб, anchor, render position и collision объекта в мире.
   Сохранить правильный предпросмотр художественного варианта.

   Расчёты размеров/преобразования выполнять с кэшированием,
   не пересчитывать всю геометрию каждый кадр или при каждом наведении.
   Ключ кэша должен различать действительно разные отображаемые модели.

3. Обновить проверку покрытия каталога.
   После дедупликации не требовать отдельной видимой записи для каждого
   технического alias. Вместо этого каждый кандидат должен:
   - иметь собственную видимую запись;
   - либо иметь доказанное перенаправление на видимый эквивалент;
   - либо быть явно исключён как служебное состояние.

   Сохранять отдельные счётчики registry IDs, видимых записей,
   художественных вариантов и скрытых эквивалентов.
   Не достигать меньшего числа простым произвольным скрытием содержимого.

4. На этом этапе не удалять registry IDs и ресурсы.
   Скрытие повтора в GUI не является очисткой самого мода.
   Не выдавать одно за другое.

ПОСЛЕ КОРОТКОГО ПАТЧА — ПЕРЕЙТИ К ПОЛНОМУ ГОРОДУ

Не создавать очередной самостоятельный цикл TEST4 переделки окна.
Не ждать ещё одного разрешения на уже предусмотренный диагностический проход.

Используй существующий конвертер и накопленные доказательства.
Сначала проверь, что проверенные shared-ownership возможности действительно
подключены к целевому диагностическому режиму, а не остались разрешёнными
только для двух тестовых fixtures.

Не включай их безусловно для всех конфликтов:
сохрани ограничения preflight, защиты чужих блоков и root/root конфликтов.

Сделай один новый полный диагностический проход на ОТДЕЛЬНОЙ КОПИИ
последнего подтверждённого MODDED-бэкапа.
Не использовать сломанную beta.3 как вход и не подменять MODDED-мир
ванильной исходной картой.

Обязательно сохранить:
- целостность доказанных составных объектов;
- ранее принятые ручные решения;
- посторонние блоки, данные и окружение;
- клеточную физику;
- отсутствие независимого fragment fallback для известных сборок.

После запуска выдать СВЕЖИЕ показатели:
- успешно восстановленные объекты и группы;
- не прошедшие группы по повторяющимся причинам;
- число затронутых уникальных семейств, где оно достоверно вычисляется;
- protected/composite failures;
- orphan helpers, неизвестные и старые ID;
- сохранность данных и результат второго прохода.

Не переносить старые числа в новый отчёт как будто они пересчитаны.
Не складывать memberships, группы и экземпляры объектов.
Не перезапускать полное историческое исследование без конкретного блокера.

Проверки не ослаблять. При провале сохранить диагностический результат,
исправлять конкретные повторяющиеся причины, не объявлять карту готовой.

ОЧИСТКА МОДА И ФИНАЛ

После успешной полной конвертации:
- определить legacy/technical IDs, которым есть доказанная замена;
- проверить их отсутствие в итоговом мире и поддерживаемых сохраняемых данных;
- проверить ссылки из кода, предметов, моделей, состояний и ресурсов;
- удалить только доказанно ненужные runtime-записи и недостижимые ресурсы.

Сохранить необходимые художественные варианты и строительные предметы,
даже если они не встречаются в конкретной карте.
Архивные данные для воспроизводимости конвертера не обязаны входить в JAR.

После очистки повторно проверить загрузку итогового мира, целостность объектов
и ресурсы JAR. Не удалять старые сохранения и не обещать совместимость
с ними, если она больше не обеспечивается.

Итоговые материалы:
- один рабочий JAR;
- один полностью конвертированный мир;
- краткий отчёт с проверками и контрольными суммами;
- актуальный экспорт JSON-моделей и текстур для художественной работы.

До прохождения итоговых проверок работать в repair-ветке.
Не делать force-push и не переносить неготовую карту в main.
