# Что полезно для Bloodborne-Blocks: полный список и мнение

Дата: 2026-10-03. Основание — предоставленные архивы, их контрольные суммы, декомпиляция CFR 0.152, полный офлайн-аудит миров, реальный Minecraft BlockModel parser и ограниченные серверные запуски. Графическая оценка в игровом клиенте не выполнялась.

## Удалось ли запустить мод локально

**Полноценный запуск чужого мода не подтверждён.** В отдельном локальном Forge 1.18.2 / 40.2.21 dedicated-профиле без GeckoLib загрузка прекращается на отсутствии класса GeckoLib. С предоставленным GeckoLib 3.0.57 загрузка прекращается на клиентском `com.mojang.blaze3d.vertex.PoseStack` в общем обработчике событий. До готовности сервера и открытия копии v16 этот запуск не дошёл. Exit code при этом равен 0; он не свидетельствует об успехе.

Копия v14 без чужого мода успешно открылась, сохранилась и повторно запустилась на Forge 1.18.2. Копия VladraCastle успешно прошла те же проверки на vanilla 1.20.1. Запуск Vladra на 1.18.2, сделанный до определения её версии, исключён из доказательств совместимости. Графический клиент, integrated server, бой, прохождение, FPS и взаимодействие двух игроков не проверены. Падение dedicated-сервера не доказывает, что клиент автора тоже падает: клиент содержит PoseStack, которого нет на headless server.

Исчерпывающие ID, пути и размещения: [FULL-INVENTORY.md](FULL-INVENTORY.md). Реестр содержит **98 entity IDs, 103 обычных item IDs и ещё 18 spawn eggs: всего 121 item ID**. Предыдущая краткая сводка ошибочно включала яйца в 103; здесь подсчёт исправлен по двум DeferredRegister.

## Инструменты автора карты

Это особенно полезное направление для удобства нашей работы. Возможность оператора удобно поставить объект часто важнее добавления очередных сотен технических вариантов.

1. `rotator`, `rotator_small`, `rotator_reset`: крупный/малый поворот и сброс. Для нашей voxel-архитектуры предлагать только поддерживаемые геометрией transforms; произвольный yaw entity не равен корректному повороту collision.
2. `hour`, `anti_hour`: тонкая корректировка направления; ToolItem содержит шаг 2.5°. Идея удобна для отдельного свободного реквизита, но не для обхода block-grid ownership.
3. `up`, `down`, `north`, `south`, `east`, `west`: смещение; ToolItem использует шаг 0.125 блока. Хороший ориентир для preview/editor workflow со snap, проверкой занятых клеток и server bounds.
4. `enlarge`, `shrink`, `reset_size`, `enlarge_percentage`, `shrink_percentage`: масштаб и сброс. Поддерживать лишь согласованные размеры, обновляя support/outline/collision вместе с render, либо явно ограничить инструмент визуальным décor type.
5. `delete`: удаление объекта. Для нас — удалять owner и принадлежащие ему helpers атомарно; shared cells и чужие roots сохранять.
6. `switch`: включение/выключение interactability. Полезна настройка объекта, но она должна иметь явное сохраняемое server state и права.
7. `freeze_mobs`, `unfreeze_mobs`: постановка/освобождение персонажей для сцен. Полезно для авторинга; требуется разграничение builder/admin permissions.
8. `target_dummy`: тестовая цель. Полезна для отдельной боевой подсистемы и измерения атак, не решает архитектурные дефекты.

Наличие этих классов не является подтверждением их пригодности для публичного сервера: permissions, sync, недопустимый target, крайние значения, save/restart и удаление требуют отдельных тестов. Инструменты нельзя раздавать всем игрокам по умолчанию.

## Игровые идеи: полезны, но за пределами текущего ремонта архитектуры

- Три семейства trick weapons: Saw Cleaver, Saw Spear, Boom Hammer, каждое с двумя item forms. Полезны дизайн переключения, разделение состояний и наборы анимаций; числовой баланс и сетевое состояние нужно оценивать отдельно. Огнестрельное оружие игрока не следует обещать по одному entity `bullet`.
- `blood_vial`: расходуемое лечение; пригодно как сценарий UX, не как готовая совместимая Fabric-система.
- Blood Echoes и Insight: разные ресурсы прогресса. Для RP-сервера нужны заранее согласованные экономика, death rules и стабильная серверная идентичность, а не прямой перенос capability-кода.
- Health/Vitality, stamina/endurance, rally: хорошая взаимосвязь атаки, восстановления и расхода ресурса. Проверить death/respawn/reconnect обязательно: в чужом Clone-handler старые и новые capabilities берутся с original player.
- HUD, hotkeys, анимационные состояния: полезно оформление feedback. Общая/server логика должна оставаться независимой от клиентских типов.
- Переходы через фонари: хороший маршрут/shortcut дизайн; сервер должен выбирать допустимую цель из собственного реестра и проверять доступ, chunk и безопасное место.
- 18 мобов: Cleric Beast, Vicar Amelia, Scourge Beast, Blood-starved Beast, Executioner, четыре Huntsman-варианта, Huntsman Wheelchair, Large Huntsman, Carrion Crow, Giant Rat, Small Rat, Rabid Dog, Maneater Boar, Brick Troll, Rotted Corpse. Всё это зарегистрировано, но в сохранённой v16 из этого списка стоят только два Maneater Boar. Boss rooms, победы и прохождение не проверены.
- Анимации предупреждения/атаки и SoundEvent разделение idle/hurt/death/attack: полезные принципы читаемого combat feedback. Hitbox, attack timing, damage и сетевое воспроизведение требуют своей реализации и проверки.
- Spawn eggs, target dummy, freeze tools: полезны как authoring/debug средства, отдельно от пользовательского survival/RP-каталога.

Я бы держал эти системы отдельным будущим проектом/модулем с server-authoritative состоянием. Импорт всего игрового JAR сейчас увеличит поверхность ошибок и не закроет owner closure, shared-cell конфликты или historical registry нашего города.

Из карт полезны: иерархия крупных объёмов и мелкого реквизита; повторяемые фасадные ритмы; сопряжения крыш/проёмов/стен; законченные композиции транспорта, деревьев и гробов; вертикальное членение и переходы; расположение световых акцентов. Пространственная оценка здесь основана на данных мира, схемах высот и авторских изображениях. Детальный маршрут, видимость из глаз игрока и playability требуют графического обхода.

Для нашего incomplete-owner audit карта пригодна только при доказанном совпадении source state, координат и transforms у конкретного образца. Она не восстанавливает автоматически 39996 historical IDs, потерянные transient composite models или membership защищённых/shared объектов. Замена source pack без контроля способна изменить geometry migration rules.

## Мой итоговый приоритет

1. Сначала небольшая галерея: витражный фасад, повреждённое стекло, статуя, настенный фонарь, люстра, цельное дерево, экипаж, групповые гробы, дверь и интерьерный набор. Каждый объект проверять рядом с нашим аналогом без shader, затем с shader.
2. Оформлять каждый объект как semantic family: понятное основное имя, art-варианты, один согласованный placement/ownership contract. Для статичного города использовать baked geometry и наши voxel helpers.
3. Добавить builder-инструменты с preview, snap, ограничениями и atomic owner operations. Сначала поворот и безопасное удаление, затем смещения/размеры у поддерживаемого реквизита.
4. Выделить двери/ворота/рычаги в небольшую самостоятельную систему: server state, NBT, sync, bounded links, oriented collision и restart tests. Лифт рассматривать отдельной сложной задачей.
5. Сохранить старые registry IDs и source mapping. Исправлять protected objects только доказанными fixtures; не обходить текущий fail-closed audit ради красивой картинки.
6. RPG/combat/mobs оценивать после стабильной архитектуры как отдельную систему. Чужой JAR использовать для анализа идей; dedicated startup, unsafe teleport и persistence делают прямое копирование кода плохим решением.

Сильнейшая сторона материала — художественное единство и постановка законченных объектов. Слабейшая — серверный контракт: client types в common subscriber, доверие координатам клиента, общий static lamp registry, неправильный Clone-handler и физика сущностей, не соответствующая модели. Наше направление с собственной geometry и ownership целесообразно сохранить; развивать стоит палитру, каталог и удобство авторинга.

Условия в комплекте требуют согласования повторного использования artwork/code/animations/sounds. Публичная ветка содержит собственный анализ, метаданные, контрольные суммы и скрипты проверки. Оригинальные ZIP/JAR, artwork payload и декомпилированный чужой код остаются локально; исходники нашего мода в этом запросе не менялись.
