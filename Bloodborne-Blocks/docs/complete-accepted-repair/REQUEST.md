## 1. Исправить реальную ошибку охвата

В rc.2 `tools/accepted_objects_restore.py` читает закреплённый успешный ledger `docs/catalog-city-continuation/final/first.json.gz` и дополняет его уже существующими logical-owner. Отчёт считает нулевые остатки ВНУТРИ этого подтверждённого набора. Это полезное выполненное подмножество, но не доказательство, что восстановлены все экземпляры ранее согласованных семейств.

Не строить список обязательных объектов только из успешных транзакций прошлого прохода. Не считать «нет в успешном ledger» равным «не входит в задачу». Не считать нынешний production manifest из 49 families исчерпывающим списком всех старых решений: некоторые цельные модели и правила остались в исторической линии, successor mappings, CONTEXT/DEFERRED-записях или generic whole-owner представлении.

Первый ограниченный шаг — сопоставить УЖЕ СУЩЕСТВУЮЩИЕ решения и их исполнение:

- `docs/accepted-restore/REPORT.md`, `AGENT-COMMENTS.md`, `delivery.json` и текущий bridge;
- `docs/catalog-city-continuation/` и сохранённые residuals, а не только success ledger;
- `docs/NORMALIZATION-ACCEPTANCE.md`, `docs/LOGICAL-OBJECTS-STATUS.md` как исторические источники, а не заявления о текущей приёмке;
- `docs/agony-patch/PATCH-PLAN.md`, `RESULTS.md` и исходные review records по их ссылкам;
- beta-client-QA, Nightmare, C001/C009, C003, C1491, C1979 и другие existing decisions/recipes, на которые ссылаются эти документы;
- текущие production palette, definitions, authored geometry, migration/source signatures, aliases и functional tests.

Используй самый поздний явный пользовательский смысл конкретного объекта. Не восстанавливай устаревшую реализацию только потому, что она была в старом JAR. Старые планы «not implemented/not accepted» не являются доказательством готового решения. Если задача для такого типа прямо подтверждается нынешним запросом, переиспользуй имеющийся подход и данные для завершения, но не объявляй его ранее проверенным.

В существующий отчёт добавь компактную таблицу:
`решение/источник → family/рецепт/вариант → successor → размещение/поведение → чем представлено сейчас → правило преобразования → найденные экземпляры/остатки`.
Не создавай новую базу знаний, общий движок семантического распознавания или десятки отчётных слоёв. Одна таблица нужна для исполнения всех решений и проверки пропусков. Она не должна заменять написание исправлений.

Случаи, отложенные для прежнего узкого релиза только из-за отсутствия в 49-family наборе, не считать автоматически исключёнными навсегда. При этом явные решения об удалении/разделении не отменять без относящегося к ним нового требования.

## 2. Обязательные типы и правильные границы цельности

### Деревья и кусты

Восстановить ВСЕ распознаваемые по существующим источникам экземпляры согласованных деревьев и их вариантов, а не только 74 из rc.2. Одно дерево — один игровой объект, предмет, owner и единое удаление. Ствол/ветви/основание не выдаются как независимые части этого дерева.

Для кустов использовать цельные авторские bush/grass модели и сохранившиеся решения, включая исторические `o_grass_*` там, где доказано соответствие. Один куст может занимать несколько технических клеток, оставаясь одним объектом. Не спутать куст с веткой большого дерева и не склеивать несколько соседних кустов в один участок растительности.

Сохранить утверждённые варианты, масштаб, текстуры, pivot, стволовую/мягкую физику. Не делать из дерева многоклеточный сплошной AABB по кроне.

### Книги, надгробия и составной реквизит

Одна согласованная авторская стопка книг — один объект. Проверять не только 34 ранее удачных места. Историческая точка `(-332,77,-137)` — известный остаток: использовать сохранённые source recipes/компоненты, а не повторять «не входит в ledger» как окончательное решение.

Не отменять разделение C003: книги, мешок, бочка, чемоданы — разные осмысленные предметы. Не склеивать всю уличную сцену в один объект.

Полная авторская композиция `gathered-grave` должна оставаться одной композицией; её технические части не должны продаваться/ломаться независимо. Отдельные tombstone-модели и явно утверждённые C1491_a/b/c сохранять самостоятельными. Не превращать близко стоящие независимые могилы в одно кладбище. По исходной модели/составу определить, что изображено на приложенном снимке, и зафиксировать границу.

C474, C471, статуи, pedestal/trim-композиции и остальные ранее согласованные цельные элементы также проверить на покрытие мира. Не считать целое историческое `owner_*` автоматически конечной семантической моделью: один старый carrier мог быть только секцией требуемого предмета.

### Двери и ворота

Для всех согласованных door/header/gate семейств восстановить не только artwork, но и функциональные canonical state machines. Technical `city_*` или generic `owner_*` с картинкой двери не заменяет дверь.

Проверить три восстановленных деревянных семейства, C282, ворота и остальные подтверждённые door recipes: один предмет, неподвижная коробка/верх, движение только створок, открытие/закрытие, проход при открытии, непропускание при закрытии, один drop, единое удаление, сохранение состояния.

Если логический ID уже правильный, воспроизведи конкретный дефект runtime: маршрутизацию use/pick/break через root/helper, состояние соседей, collision и post-update. Не объяснять любую неисправность только неправильным ID и не требовать от пользователя снова найти все двери.

### Лестницы и площадки

Повторяющаяся утверждённая секция лестницы — один многоклеточный объект; следующая секция ставится сверху штатным способом. Не склеивать всю произвольную длину лестницы в один гигантский новый предмет.

Для `o_ladder_03` и подтверждённых aliases проверить реальное лазание через стыки нескольких секций, правильную сторону установки, отсутствие прохода поперёк закрытой физической плоскости, постановку соседних блоков, независимое снятие и возвращение секции.

У `o_ladder_01` сохранить всю опорную поверхность и правильный переход с лестницы. Это отдельная площадка по старому решению, а не ступенька, которую снова нужно сделать climbable.

Не возвращать удалённый `o_ladder_02` просто потому, что он есть в старом архиве. Его прежняя судьба и действительные самостоятельные replacements проверяются по решениям, а не по соседству.

### Фонари, столбы, кронштейны

Восстановить согласованную цельную конструкцию СТОЛБА/КРОНШТЕЙНА; отдельный маленький `o_lantern` не закрывает требование цельности столба. Не приписывать историческому отчёту готовую сборку там, где было написано «не установлена».

Где пользователь согласовал съёмный фонарь, столб остаётся цельным самостоятельным объектом, фонарь — присоединяемым элементом. Не объединять без разбора все близкие светильники и статуи в один предмет.

Переиспользовать существующие точки крепления, lit/unlit artwork и attachment runtime. Проверить правильную ручную установку в той же системе координат, включение/выключение, снятие/возврат и сохранность соседнего owner. Принятое крепление к статуям не ломать.

### Ограждения, стены, бордюры

Восстановить не только возможность получить новый предмет, но и ПОВЕДЕНИЕ уже размещённых соответствующих секций города. `pick` с alias, дающий правильную ограду, недостаточен, если оставшаяся на карте секция не поворачивается и не обновляет соединения.

Для подтверждённого типа преобразовать исторические X/Z/connection aliases в строительное семейство с нужными state properties. Сохранить разные художественные семейства как разные блоки. Использовать уже сделанный `building_stone_brick_wall`, `o_stone_railing`, бордюр и подтверждённые balustrade adapters, а не написать их заново.

Не считать любой каменный блок с полосой оградой. Для показанной «Коричневый камень с верхним поясом» и других спорных имён определить исходную модель/recipe и назначение по данным. Нормализация должна касаться именно ограды, не соседнего обычного материала.

Проверить ориентации, линию, угол, T/крест в пределах имеющегося artwork, вертикальные стыки, добавление/удаление соседей и сохранность guest ownership. Не изобретать новую художественную геометрию там, где достаточно существующих вариантов. Поддерживаемые/неподдерживаемые формы записать честно.

## 3. Единственная новая функциональная правка окна

Положение окна TEST3/rc.2, подоконник, масштаб, UV, направления раскрытия, две физические/storage клетки, наведение и независимый задник уже приняты. Не переделывать их.

НОВОЕ явное требование пользователя, заменяющее старое требование двух кубов для open:

- `open=false`: две полные клеточные collision, как сейчас; пройти нельзя.
- `open=true`: СОБСТВЕННАЯ collision окна в обеих клетках пустая; игрок может пройти через проём.
- Область хранения/ownership остаётся root + helper сверху. Пустая collision не означает удалить helper, сделать его воздухом или разрушить окно.
- Outline/selection/use сохраняются, чтобы окно можно было закрыть, выбрать и сломать. Их нельзя подменить пустой collision.
- Существующая collision других владельцев общей клетки и обычной стены позади не исчезает. Для прохода через стену игрок оставляет настоящий проём; мод не режет стену и не делает её прозрачной.
- Root и helper используют актуальное open-состояние одного окна; открыть у root, а оставить закрытую физику у helper недопустимо.

Проверить движение реального игрока через свободный проём 1×2 в open, блокировку в closed, клики по обеим частям, четыре facing, BASE/ALT, смену состояния рядом с игроком, save/restart и границу чанков. Коллизия не должна появляться от декоративных открытых ставней.

Обновить только соответствующие оконные ожидания в тестах. Это санкционированная смена требования, не повод ослабить остальные frozen contracts или автоматически обновить все эталоны по новому коду.

## 4. Клеточная физика без повторного разрезания моделей

Раздельно сохранять semantic identity, source assembly, root/storage footprint, gameplay collision, selection и render. Они не обязаны иметь одинаковые границы.

Collision каждой принадлежащей объекту клетки хранится локально в [0,1] по всем осям. Цельный многоклеточный объект остаётся цельным. Визуальные выступы не резервируют дополнительные клетки автоматически. Пустая collision не отменяет storage membership.

Все уже принятые ручные формы сохранить, кроме разрешённой выше open-collision окна. Для новых/восстановленных ранее согласованных семейств использовать готовые формы и простые предусмотренные ими коллизии. Не включать произвольное упрощение всех 54 тысяч states и не нормализовать render до одного куба.

Оставленные в rc.2 физические профили 2 914 compatibility ID не являются запретом исправлять подтверждённый функциональный successor. Для преобразуемого объекта разрешён переход на правильную согласованную физику; неизменность относится к нецелевому окружению. Не возвращать blanket one-cell physics всем объектам и не делать новые массовые root-сдвиги.

## 5. Полнота обработки вместо отчёта только об успехах

До записи построить независимый список кандидатов по существующим source census, decisions, aliases, recipes и текущим rc.2 palettes/остаткам. Проверка обнаружения не должна читать только выход success ledger конвертера.

Для каждой релевантной family/варианта считать отдельно:
`кандидаты → уже правильные → восстановленные → реально отсутствуют → явно superseded → неразрешённые известные → подлинно неизвестные`.
Любое исключение должно быть объяснено. Ноль в success ledger не является доказательством отсутствия family в городе. Отсутствие формы в 49-family manifest не является доказательством, что прежнее решение отменено.

Не начинать новую геометрическую археологию по каждой координате. Сначала использовать готовые recipes/исходники/сохранённые records и сопоставить уже известные цепочки `original → MODDED → rc.1 → rc.2` для целевых семейств. Сопоставления одинакового recipe кэшировать; различать действительно художественные варианты, weighted-состояния и контекстные компоненты.

Расширять существующий converter/bridge только необходимыми отображениями и функциональными successors. Доказанная однотипная причина чинится для ВСЕХ экземпляров данного типа, а не координатным исключением только для скриншота.

Сходство названия, общий материал и близость не доказывают одно владение. Не выполнять глобальный replace белой/оранжевой шерсти, city_column или всей растительности.

До атомарной замены проверять текущее содержимое rc.2, чужие данные, полную зависимую группу и ожидаемую геометрию. Сохранить уже работающий shared-ownership механизм; не сочинять новую систему поверх него. Удалять только технические source parts именно заменяемого объекта. Не переносить окружающие здания и не стирать чужие блоки ради PASS.

Если старые sources действительно не различают два согласованных результата (например, известная неоднозначность C046/CASES), сохранить явно принятое решение. Не повторять сканирование всей карты в надежде получить отсутствующий признак. Если необходимое решение отсутствует, перечислить только конкретную остаточную неоднозначность и продолжить независимые задачи; не переписывать остальные группы по догадке.

## 6. Неизвестные ID: разрешение не останавливать работу

Пользователь разрешает удалять либо игнорировать подлинно неизвестные ID. Их восстановление не должно блокировать эту задачу.

Различать:
1. реально недоступный Bloodborne ID без доступной definition/model/mapping после ограниченной проверки сохранённых источников;
2. известный city/carrier/owner или известная модель, для которой пока не найдено правильное соединение;
3. ID другого мода, отсутствующего только в урезанной QA-сборке.

Разрешение на удаление относится к пункту 1, НЕ к 2 или 3.

В итоговой копии недоступные Bloodborne block IDs допустимо заменить воздухом с журналом dimension/coordinates/before/reason и проверкой block entities/ticks/ownership. Сохранить резервный вход. Не оставлять в публикуемой карте заведомо незагружаемые неизвестные ID, ссылаясь на «игнорирование»; игнорировать можно их художественную реконструкцию. Не вводить ложные placeholders только ради нулевого census.

Не удалять fragment известного дерева/двери как «неизвестный» из-за неподтверждённого owner или отсутствия его в success ledger. Не повторно очищать координаты прежних 33 удалений: в rc.1/rc.2 часть занята уже известными другими состояниями; проверять фактическое текущее содержимое, не исторический список координат вслепую.

Данные других модов и player data не удалять. Наличие только Bloodborne+Fabric в QA не является доказательством неизвестности стороннего ID. Сложный случай с посторонним NBT не должен приводить к потере чужих данных; сообщить ровно этот блокер.

## 7. Экономный порядок реализации и реальные тесты

1. Сохранить рабочие изменения, проверить фактический rc.2, закрепить короткую таблицу существующих решений/пропусков. Не повторять историю всех веток или аудит bytecode старой beta.3.
2. Взять по одному живому неуспешному примеру каждого класса из текущего города и сделать воспроизведение ДО исправления. Не выбирать снова только удачные деревья/книги из старого ledger.
3. Исправить повторяющиеся причины: пропущенный successor, недоступный в палитре старый целый рецепт, слишком узкое распознавание current carrier, generic model вместо functional block, устаревшие aliases ограды. Использовать существующие runtime и compiler.
4. Прогонять быстрые проверки изменённого класса; не запускать весь мир после каждой правки в документе. После интеграции — один полный проход по копии rc.2, независимый остаточный поиск, затем точечные фиксы реального остатка и итоговая верификация.
5. Проверить упакованный JAR и поставляемую карту одной версии, не отдельные JSON и искусственную площадку вместо реального города.

Обязательные действия на исправленных образцах:
- pick из реального города → поставить на свободное место → четыре ориентации → удалить за доступную часть → один корректный предмет → сохранить/загрузить;
- отсутствие самостоятельных остатков принадлежащих объекту частей;
- двери: use → фактическое открытие → движение игрока через проём → закрытие; также взаимодействие через helper;
- лестница: несколько секций, реальное движение по всей высоте через стыки, площадка, удалить/вернуть секцию;
- ограды: реальная установка предметом и обновления соединений после изменения соседей, включая уже конвертированные секции;
- фонарь: целая опора и корректное крепление/свет согласно принятому решению;
- открытое/закрытое окно согласно разделу 3;
- остальные ранее принятые семейства — regression, без нового дизайна.

Проверка только наличия ID, хеша meshes, метода isClimbing или собственного отчёта конвертера недостаточна. Тест, который видит исчезнувшую family как «0 проверено → PASS», ошибочен. Сохранять тесты старого неверного результата как отрицательные примеры, а не принимать их за новый эталон.

Для минимум одного тестового экземпляра каждого исправляемого класса использовать исходные данные НЕ из того же success ledger, которым задана ожидаемая выдача конвертера. Проверять и coverage, и результат.

Не обещать игровой визуальный PASS без настоящего клиента. Серверный movement/use/save/restart выполнить в доступном окружении, указав состав QA-модов. Урезанная QA-копия не заменяет публикуемый мир; чужие данные сохраняются в поставляемом ZIP.

## 8. Что считать завершением и что публиковать

Не сокращать критерий обратно до окна+74 деревьев+34 стопок. Требуется проверить и применить весь набор существующих решений по затронутым типам и сохранить остальные принятые объекты.

Для всех идентифицированных экземпляров согласованных семейств должны отсутствовать необъяснённые known fragments и функциональные регрессии. Отдельно перечислить действительно неразличимые/неполученные исходные случаи; не назвать их подлинно неизвестными только для обхода проверки. Не объявлять «всё завершено», пока известные целевые дефекты остались.

Подлинно недоступные ID обрабатываются разрешённым удалением и не заставляют начинать ещё один общий исследовательский этап. Незатронутые новые художественные пожелания и глобальная оптимизация не входят в задачу.

Перед выпуском:
- совпадение необходимых runtime/resources с принятыми источниками плюс документированный open-window patch;
- независимый census всех исходных кандидатов и остаточных старых представлений;
- отсутствие unknown/invalid states/orphan helpers после разрешённой очистки;
- сохранность нецелевых cells/NBT и сторонних данных;
- повторный проход без новых изменений;
- полноценные функциональные проверки целевых семейств.

Добавить эти требования в существующий release gate. Два разных результата должны быть видны отдельно: «проверки выполненного подмножества PASS» и «полнота применения всех целевых решений PASS/FAIL». Первый не разрешает подменять второй.

Результат: JAR, полная исправленная копия rc.2 города, короткий README, координаты реальных исправленных и оставшихся случаев, таблица counts по семействам, SHA-256 и source commit. Номер взять следующий свободный, без перезаписи rc.2. Сохранить исправления GUI/каталога, не выполнять ещё одну массовую очистку registry ради уменьшения числа ID. Новый экспорт художественных ресурсов нужен только при фактическом изменении соответствующих ресурсов; существующий актуальный комплект не генерировать повторно без причины.

Проверить `git status` и другие работы проекта; вести исправление отдельной рабочей веткой от актуального main. Сохранять осмысленные checkpoint-коммиты, без force-push, reset или утраты local WIP. После целевых проверок интегрировать согласованный результат в main, сохранив сторонние изменения. Выполнить push исходников, необходимых resources, отчётов, JAR и мира; Git LFS-объекты тоже загрузить. Проверить удалённый HEAD, доступность файлов и SHA скачанных артефактов. Локальный commit не считать публикацией.

Если работа остановлена реальным блокером — опубликовать checkpoint в рабочей ветке, сохранить рабочие части и перечислить только необходимое недостающее решение/источник. Не публиковать в main ложный «полностью исправленный» комплект. Не заканчивать просто обещанием продолжать: отдать фактический checkpoint и результат.

**Главный смысл: не переизобретать уже согласованные объекты, а обеспечить полноту применения их правильной структуры и поведения ко всему поставляемому городу.**
