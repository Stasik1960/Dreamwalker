Разделяй редактирование оформления и обычную игровую функцию. Открывание/закрывание входной двери, использование рычага и автоматические соединения ограды остаются своими взаимодействиями. Инструмент должен выдавать изменение только в предусмотренном режиме строительства/с правами редактирования. Простого наличия инструмента недостаточно для обхода запрета обычному игроку. Административные команды изменения вида также сохраняют соответствующие права. Опиши, какие действия являются оформлением, а какие — игровой функцией.

9. ОБЩИЙ ПРИОРИТЕТ: ПРОСТАЯ И НЕДОРОГАЯ ФИЗИКА

Это новое уточнение ослабляет прежнее требование точного повторения видимого контура коллизией. Приоритет: рабочая функция и необходимые проходы; затем низкая стоимость физики; затем точность её соответствия художественному контуру.

Частичный заход игрока в видимую модель допустим. Не собирай физику по каждому декоративному элементу ради точного силуэта. При этом не закрывай проход огромной невидимой коробкой, не оставляй препятствие в открытой двери и не делай проходимый куст твёрдым.

В отчёте покажи отдельно число физических объёмов, объёмов выделения, служебных клеток и зарегистрированных состояний до/после. 1. Числовые ID и самостоятельные модели

Каждый самостоятельный строительный тип и каждое самостоятельное художественное исполнение, доступное отдельным предметом, должны иметь уникальный ID из пяти цифр. Больше не используй сочетание «90004 + вариант N» как идентификатор самостоятельной модели. Это уточнение заменяет прежнее разрешение объединять разные выбираемые художественные исполнения под одним ID.

Поворот, плоскость установки, открытие/закрытие, соединение ограды с соседями, BASE/ALT и другие предусмотренные состояния одного объекта сохраняются внутри одного типа. Для этих состояний отдельные ID не создаются. Переключение видимости собаки внутри клетки тоже является состоянием конкретной клетки.

Одинаковая модель, только повёрнутая иначе, не становится новым самостоятельным художественным типом. Ограничение углов остекления описано отдельно ниже. Общий код, текстуры и модели можно переиспользовать между типами; одинаковый код не означает общий пользовательский ID.

В ближайшей тестовой версии каждому оставленному самостоятельному исполнению присвой отдельный пятизначный TEMP-ID, показывай его в имени, Creative, tooltip и /bb debug. Составь таблицу «старый ID + старый вариант → новый ID / исключённая форма». Уже используемые номера не переиспользуй для других объектов. Для существующих предметов и сохранений обеспечь явное преобразование, чтобы они не стали воздухом или предметом другой модели.

Прежнее требование окончательного распределения ID по частоте использования на полной карте сохраняется. TEMP-ID не объявляй окончательным; переход TEMP→FINAL должен иметь таблицу соответствий и обработку сохранённых данных. Для окончательных архитектурных registry ID используй числовую часть вида bloodborne_dw:12345: namespace Minecraft сохраняется. Технические helper-ячейки не являются отдельными пользовательскими блоками и при отладке показывают ID своего владельца. Сохранность старых RP registry IDs, UUID, CustomName, NBT и связей обеспечивай совместимостью/миграцией; простое переименование всех RP-регистраций недопустимо.

Наличие правильного NBT само по себе не закрывает замечание. Сравни модели с обеих сторон: некоторые исходные поверхности одинаковы, но это не разрешает заменять выбранный тип первым.

Для обычной установки и редакторского вращения этого остекления оставь только ориентации, кратные 90°, и положения вертикально, горизонтально на полу и горизонтально под потолком. 8. Исключение для пересекающихся коллизий при конвертации

Уточняю прежние мягкие правила: визуальное пересечение моделей и касание поверхностей разрешены. При ОБЫЧНОЙ НОВОЙ установке объёмное пересечение активных твёрдых коллизий, составляющее конфликт, должно запрещаться. Эта часть нового уточнения заменяет прежнее общее разрешение физического пересечения. Проходимые части, пустые формы, декоративные выступы и AABB визуального габарита сами по себе не являются конфликтом. Проверка должна учитывать реальные активные формы и допуск на численную погрешность, а не запрещать обычное соседство.

Только при первоначальной конвертации конкретных существующих объектов карты допускается обход этой проверки, чтобы сохранить их исходное расположение при наложении коллизий. Коллизии продолжают работать для игрока; исключение не превращает их в noclip и не удаляет физику одного из объектов.

Это разрешение относится к перенесённым экземплярам, а не ко всем объектам соответствующего ID. Оно не передаётся предметам через выпадание, middle pick или копирование инструментом. После разрушения повторная установка является новой и проходит обычную проверку: при оставшемся конфликте она запрещена. Загрузка/перезапуск сохранённого мира сохраняют уже перенесённое расположение, но не дают новое разрешение на принудительную установку. Повторный запуск конвертера должен быть идемпотентным.

В v8 FabricCompositeWorld.allowsReviewedOverlap всегда возвращает true, а установка RP-декораций тоже не проверяет физическое пересечение с архитектурой. Это ещё не реализация описанного ограничения. Раздели обычную установку и разрешение конкретного переноса. Обход физической проверки не разрешает перезаписывать чужие блоки, block entity, инвентари или данные владельцев: используй сохранение независимых вкладов/ownership. Если конкретная ситуация не представима текущим форматом данных, вынеси её в отчёт как нерешённую, не скрывай потерю объекта.
