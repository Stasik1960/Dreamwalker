# Новый runtime-план после Starlight deadlock

Это план, не доказательство успешного запуска. Candidate7 и его MIN14/REENTER3 результаты сохраняют исходные SHA/status. FULL release3 attempt1 завершён принудительно после подтверждённого deadlock; штатное сохранение этого процесса не заявляется. Production main8 заморожен: SHA256 `884ba57ce8ba0a64e3fdc5dd8730c3945a44d1a35f462cea39245301b2e69e75`, 133 native tests и 20 core checks PASS. QA21 не собрался из-за трёх вызовов API текста; исправлена только сериализация `Text.Serializer.toJson` для 1.20.1. QA22 собран и заморожен; MIN15 прошёл ограниченные 69 canonical + 7 alias middle-pick/re-placement проверки, но завершился общим FAIL на восстановлении клиентского инвентаря перед меню. QA23 source-only fix и isolated Java17 compile готовы, полный новый клиентский запуск ещё требуется. Свежие Author7, minimal production reopen5 и full-owned-scene reopen4 фактически прошли; дальнейшие клиентские PASS ими не подменяются.

Исторические незапущенные аргументы находятся в `tools/review_v10_candidate8_runtime_plan.json`. Генератор по умолчанию описывает QA21; для текущего запуска root явно передаёт `--qa-jar build/frozen-artifacts/v10-qa-22/dreamwalker-first-set-review-qa-0.1.0-prototype.5.jar` и записывает новый `tools/review_v10_candidate8_runtime_bound.json` после сборки QA22. Файл содержит `UNBOUND_MAIN8_QA20_NOT_BUILT_NOT_RUN`, неизвестный SHA обозначен `__FROZEN_MAIN8_SHA256__`. Команды с ним выполнять нельзя. `tools/prepare_review_v10_candidate8_plan.py` только записывает аргументы, не запускает Minecraft/Gradle. После настоящей заморозки root может передать `--jar`, `--qa-jar`, `--artifact-sha` и новый `--output`; helper сравнит bytes JAR с SHA и запишет новый bound-план. Существующие доказательства не перезаписываются.

Последовательность фактических запусков:

1. Author7 создаёт свежий мир; отдельный typed patch7 заранее устанавливает Creative/cheats. Production-only minimal reopen5 и full-profile owned-scene reopen4 открывают копии свежего Author7 без QA. Старый empty-world full startup остаётся другим режимом и другим доказательством.
2. После их штатной остановки два вызова `verify_review_v10_pristine_reopen.py` проверяют сохранённые native state/full typed BE, resident UUID/payload, owner ledger, объявленные RP identity/pose/control fields и pristine rules/lamp state. Vanilla metadata, генерируемые chunks и transient RP NBT не объявляются байт-в-байт неизменными.
3. Маркеры4 AUTHOR, REENTER и strict shader создаются только из фактического PASS Author7 и нового JAR. Для shader переносятся только заявленные имя Kappa и 42 option values; это не перенос старого shader PASS.
4. Dedicated diagnostics4 выполняет OFF60, ON60 с auto-expiry/export и REENTER из сохранённого ON. Во время измерений отсутствуют другие игровые процессы, сборки и тяжёлые hash/world/ZIP проверки.
5. MIN15 использует pristine Author7. REENTER4 загружает сохранённый MIN15 мир. FULL4 с полным client-профилем, 6 GB и Kappa/42 settings использует новую копию pristine Author7. Каждый процесс должен завершиться со своим настоящим PASS и normal save/exit0 до следующего. Integrated FULL4 является отдельной проверкой Starlight worker/rendering path.
6. Во всех трёх клиентских режимах дополнительно требуются 69 настоящих нажатий pickItemKey по canonical RP. В AUTHOR/FULL добавлены семь технически созданных old-registry экземпляров с настоящим клиентским pickItemKey и одна обычная повторная установка полученного предмета: новый UUID, сохранённые настройки/имя, без переноса Links/offset/source provenance. Native support, исходные экземпляры до удаления и исходный vanilla inventory проверяются отдельно. Это подготовленный QA-код, ещё не actual PASS.
7. Alias release2 содержит три самостоятельных процесса: fresh AUTHOR с 14 old registry instances и 7 inventory stacks, disk REENTER с compatibility probes и production-only restart. Независимый typed reader требуется после всех трёх. Direct server `getPickBlockStack()` является API-доказательством, не реальным нажатием средней кнопки клиента.
8. После окончания игровых процессов независимые roster/menu/diagnostics/alias проверки получают новые отчёты. Архив delivery создаётся из production-only reopen5 pristine baseline; изменённый GUI AUTHOR/REENTER graph остаётся отдельным доказательством и не импортируется в доставляемую сцену.

Опция `--full-scene-copy` добавлена в `run_review_v10_candidate_servers.py` явно. Без неё поведение и status старого startup-only pipeline сохранены. С ней full-процесс копирует только свежий Author baseline, исключает QA и требует byte-copy/source-unchanged proof. Его отдельный status — `PASS_AUTHOR_REOPEN_FULL_SCENE_FRESH_MARKERS_DIAGNOSTICS_WAITING_SEPARATE_GO`; это status этапа, который появится только после фактических запусков.

Можно объединить независимые post-stop чтения в одной Python стадии или использовать общий неизменяемый inventory cache. При этом каждый wrapper/run/profile/SHA и результат проверки остаются отдельными. Нельзя подменять restart физикой/рендером, full-server integrated клиентом, canonical69 hidden alias disk proof, или прежний PASS новым SHA. Существующие art/semantic отчёты допустимо ссылать только вместе с явным current-input byte/contract comparison; их старый artifact SHA не исправляется.

Минимальные проверки Python для подготовленного tooling: `py_compile` трёх изменённых/новых helpers и `--help` проходят. Новые runtime, saved-world audits, archive/package, ручная visual-приёмка и полная конвертация города здесь не выполнялись. GPU time и причинная FPS/CPU доля не установлены.
