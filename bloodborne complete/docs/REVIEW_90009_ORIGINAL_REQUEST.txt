2. ОСТАВИТЬ ТОЛЬКО 90009

90008 (bloodborne_dw:builder_tool) удалить как отдельный доступный инструмент. Единственный рабочий инструмент — 90009 (bloodborne_dw:composite_builder). Сохранить все функции в 90009, исправить название, подсказки, Creative-вкладку, документацию и тестовую площадку.

Не уничтожать старые предметы 90008 в сохранениях. Реализовать безопасный переход к 90009 при загрузке/использовании с сохранением совместимых настроек предмета. При необходимости старое registry-имя может остаться скрытым техническим переходником для чтения старых сохранений; это не второй предлагаемый инструмент. Не обходить ради миграции все чанки мира. Номер 90008 считать выведенным из использования и не присваивать другому типу.

После перехода игрок видит и получает 90009, а не два одинаковых предмета. Проверить старый 90008 в инвентаре, сундуке и как выпавший предмет. Старые режимы, если они хранятся числом enum, читать совместимо: перестановка режима в новом меню не должна превращать старую настройку в другое действие.

4. БЫСТРОЕ УПРАВЛЕНИЕ В ИГРЕ

Предпочтительная схема — контекстный инструмент с закреплённым выбором, подсветкой и небольшой панелью над хотбаром. Ориентир по принципу взаимодействия — Litematica: выбор в сцене, клавиши/колесо для частых операций, отдельные настройки для сложных задач. Копировать весь интерфейс Litematica или вводить полноценный 3D-редактор не требуется.
Официальные примеры принципа:
https://github.com/maruohon/litematica/wiki
https://github.com/maruohon/litematica/discussions/791

Управление по умолчанию:
— ЛКМ в режиме «Выбор»: закрепить конкретный экземпляр.
— Ctrl + колесо: переключить доступное действие без открытия меню. Прокрутка при этом не переключает слот хотбара.
— ЛКМ в режиме операции: один шаг выбранного действия.
— Shift + ЛКМ: обратное действие — поворот в другую сторону, спуск вместо подъёма, предыдущая допустимая монтажная плоскость и т.п.
— Alt + колесо: изменить шаг высоты между 1/16, 1/8, 1/4, 1; подсказка отражает реальный шаг. Для поворота использовать только допустимые углы типа.
— ПКМ: открыть компактные настройки текущего объекта/режима без изменения объекта.
— Ctrl + Z: отменить последнее поддерживаемое изменение инструмента.
— клавиша X, доступная для переназначения: отменить текущий рабочий выбор/связывание. Она не удаляет уже сохранённые связи.
— средний клик инструментом: выбрать другой объект; при перекрытии последовательно выбирать кандидатов под прицелом. Обычный pick без инструмента сохранить.
— Esc в меню: закрыть меню с корректной обработкой несохранённого черновика.

Комбинации должны быть переназначаемыми. При конфликте с управлением клиента показать его и разрешить изменить клавишу. Ввод перехватывать только в контексте инструмента, не при наборе текста/чате и не при обычной игре без него. В открытом меню колесо прокручивает список, а не меняет действие в мире.

Базовые быстрые режимы: «Выбор», «Поворот», «Высота», «Внешний вид/содержимое», «Монтаж», «Связать», «Разорвать», «Осмотр». Не показывать для выбранного типа бессмысленные операции. Если режима нет у нового выбранного объекта, переходить в «Выбор» с подсказкой, а не применять неожиданное действие.

В режимах геометрии действие применяется к закреплённому экземпляру, пока он доступен и находится в допустимой досягаемости: заново попадать по нему каждым кликом не нужно. Если выбора нет, первый клик только выбирает объект, следующий изменяет. Для режимов связывания источник закреплён, а ЛКМ выбирает цель под прицелом; это явно показано на экране. Переключение между поворотом и высотой не сбрасывает объект. Открытие меню также не меняет выбранный UUID.

Удержание ЛКМ не вызывает лавину операций. Инструмент в любой руке запрещает обычную поломку/удар; редактирование — основной рукой. Неподходящий объект даёт понятное объяснение. Для обычного удаления/использования убрать инструмент из обеих рук; показать это в подсказке при необходимости.

Отмена: минимум последние 20 успешных изменений геометрии/высоты/монтажа/оформления/содержимого в текущем сеансе игрока. Хранить ограниченную историю на сервере; проверять, что экземпляр существует, права сохранены, а другой игрок не изменил затрагиваемые данные. Не откатывать чужую работу. Не обещать отмену консольных команд, телепорта, игровых открытий и других необратимых побочных действий. Создание/разрыв простых связей, если отмена для них реализована, показывать как отдельную подтверждённую возможность. Масштаб и перемещение по X/Z в эту задачу не добавлять.

5. ПОНЯТНЫЙ ИНТЕРФЕЙС И ГРАФИКА В МИРЕ

Над хотбаром — компактная панель: выбранный объект и ID, текущая операция, шаг/угол, подсказки ЛКМ и Shift+ЛКМ. Названия важнее декоративных иконок. При выборе подсветка сохраняется, пока объект выбран; не исчезает через несколько секунд сама по себе.

Различать:
— объект под прицелом;
— закреплённый редактируемый объект;
— источник связи;
— подключённые цели.
Использовать разные обозначения и подписи, а не только цвет; названия и ID показывать в HUD/меню, не над энтити-блоками. Выбор инструментом не должен зависеть от точного попадания в каждую мелкую деталь модели. Его удобство не должно расширять обычную область разрушения/взаимодействия: раздел 12.6 отдельно задаёт требования к игровому наведению.

Связи показывать ограниченными линиями/стрелками для выбранного объекта/группы: рычаг → цели, фонарь ↔/→ фонарь. Показать, что связь существует, её направление, действие и причину отказа. В режиме связывания подсвечивать подходящую цель и показывать предварительную линию. Далёкие/выгруженные цели отображать меткой последнего известного положения без загрузки чанков ради визуализации. В игре это видит только редактирующий игрок, а не все участники.

ПКМ открывает компактную панель настроек; расположение:
— сверху постоянная строка выбранного объекта: название, пятизначный ID, краткое положение; UUID/registry/измерение раскрываются через «Подробности»;
— основные разделы: «Объект», «Связи», «Телепорты», «События»;
— «Диагностика» и «Управление» доступны отдельными дополнительными пунктами;
— внутри раздела сначала текущие значения/связи, затем действия; рядом с конкретной записью её редактирование и удаление;
— внизу формы — «Сохранить» и «Отмена», доступные без поиска на другой странице;
— при широкой области допустимы список слева и параметры справа; при узкой — один столбец с нормальной прокруткой и сохранённой нижней панелью.

Не строить гигантскую таблицу всех функций и не дробить каждую мелочь на отдельный экран. Иконки сопровождать понятными русскими подписями; выбранный режим выделять. Недоступные функции скрывать либо объяснять причину, если это ограничение прав/состояния. Переключатели подписывать текущим состоянием («Собака: включена»), а кнопки — действием («Скрыть собаку»): не смешивать эти два смысла.

Настройки шага/режима меняются сразу. Формы имени, группового правила и списка команд сохраняются явно. Не терять введённое при случайной смене вкладки, приходе обновления сервера или перестроении окна. При выходе с изменениями предложить «Сохранить / Не сохранять / Остаться»; обновление чужих данных не должно молча затирать черновик. Двойной клик по «Создать/Сохранить» не создаёт два правила.

Меню не ставит мир на паузу. Обычное подтверждение — короткая экранная подсказка; важная ошибка, сохранение формы, удаление связи и экспорт отчёта — дополнительно личное сообщение в чат. Успех подтверждать после принятия изменения сервером. Состояние «ожидает закрытия/загрузки» не называть завершённым.

Использовать спокойное оформление в тематике Bloodborne: читаемый текст, тёмный фон, умеренные акценты, одинаковые отступы. Не украшать интерфейс за счёт читаемости. Существующий значок 90009 можно сохранить; он должен отличаться от остальных предметов.

6. ГЕОМЕТРИЯ, МОНТАЖ И СОДЕРЖИМОЕ

Поворот и высота должны работать для всех поддерживаемых архитектурных блоков и RP-объектов. Высота — смещение всего экземпляра по мировой Y, не изменение размера модели. Сохраняются UUID, связи и настройки; вместе смещаются модель, область выбора, действующая коллизия и лестничное взаимодействие. Сброс высоты возвращает только высоту, не удаляя остальные параметры.

Игровая коллизия игрока, область выбора и ограничения размещения — отдельные вещи. RP-объекты не должны запрещать размещение обычных блоков/других RP рядом и в пересекающейся области; размещение рядом не удаляет и не активирует объект. Реальную занятую ячейку обычного корневого блока нельзя перезаписывать. Сохранить чужие блоки/инвентари, проверки прав, живых сущностей и границ мира. Не переписывать согласованную физику ради подсветки или удобного выбора.

90004/90010/90020 — три самостоятельных тонких остекления: собственный предмет/ID, поворот только на 90°, «Вертикально / Пол / Потолок», поддержка уже установленного стекла не требуется. Не возвращать угловые варианты. Для остальных типов сохранять имеющиеся допустимые повороты, включая 45°, где они предусмотрены, с явными исключениями для 90002/90012 в разделе 12.1. Эти ограничения обязательны и для инструмента 90009.

90007 — деревянные панели; 90001 — архитектурная дверь. 90006 — сохраняемая архитектурная лестница; её копии 90018/90019 выводятся из использования по разделу 12.4. 91069 — RP-лестница с платформой; 91086 — RP-ступени. Проверить инструмент на этих разных реализациях, не подменять их одним обработчиком по внешнему сходству. Дополнительное изменение коллизии 90006 ограничено указанным в разделе 12.4 случаем.

В клетках 91007/91008/91009 переключатель содержимого должен реально скрывать/показывать собаку, оставляя клетку. Проверить две одинаковые клетки с разным состоянием, анимации, смену выбора и перезаход: состояние одного экземпляра не должно протекать в другой. Это отдельная настройка содержимого, а не переименование всего объекта в BASE/ALT.

BASE/ALT и существующие декоративные положения сохранить по настоящим возможностям типа. Каждая показанная кнопка должна иметь работающий обработчик на сервере и видимый результат. Не показывать RP-объекту «положение панелей» лишь потому, что он открываемый, если действие для него не реализовано. Разделить декоративное оформление и функциональное открытие; функциональные изменения проходят обычную проверенную механику и корректные события.

7. РЫЧАГИ: ПРОСТЫЕ СВЯЗИ И РАСШИРЕННЫЕ ПРАВИЛА

91072/91073 — рычаги. Поддерживаются настоящие открываемые архитектурные и RP-объекты, включая 90001 и RP-ворота 91075; список остальных определить по реальным возможностям каталога, без выдуманных состояний.

Простая связь без меню:
1) выбрать режим «Связать»;
2) ЛКМ по рычагу — выбрать источник, показать его ID и подсветку;
3) ЛКМ по двери — сохранить связь; следующие клики по другим дверям добавляют цели того же источника;
4) показать линии и «Подключено целей: N»;
5) завершить выбор, убрать инструмент и проверить обычный ПКМ рычага.

Имя правила, отдельное создание пустого правила и «Применить» не должны требоваться для этого сценария. Простая связь по умолчанию открывает/закрывает цель. Повторный клик по уже подключённой цели сообщает «уже связано» и не плодит дубликаты. Один рычаг может управлять несколькими целями, несколько рычагов — одной целью. Сохранить принятую задержку 70 тиков; показывать ожидающее срабатывание, чтобы задержка не выглядела отказом.

В режиме «Разорвать» выбрать источник, затем нужную цель: удалить только указанную простую связь. В меню дать отдельные действия удаления цели, источника и всего правила с понятным описанием последствий. Отмена рабочего выбора не разрывает сохранённые связи.

Для групповых правил в меню: имя, источники, цели, условие «Любой / Все», действие «Открывать и закрывать / Только открывать / Только закрывать», отдельное импульсное действие по возможностям цели. Создание нового сложного правила — черновик до сохранения валидного состава; пустые записи от быстрых кликов не засоряют мир.

Сохранить смысл существующей v10:
— «Любой»: каждое успешное срабатывание одного источника выполняет выбранное действие;
— «Все»: учитываются сохраняемые логические признаки источников, а не только короткая анимация;
— для «Все, открывать и закрывать» выполнение условия открывает цели, нарушение закрывает;
— «Только открывать/закрывать» выполняется при достижении условия, без автоматического обратного действия при его нарушении;
— сброс логических признаков отдельно подтверждается и не имитирует нажатие рычага;
— удалённый обязательный участник делает «Все» неполным; выгрузка чанка не считается удалением.

Основной список показывает связи выбранного экземпляра. Глобальный список — отдельный режим администратора. Порядковые номера для человека начинаются с 1 в текущем списке; внутренние UUID/порядок исполнения могут оставаться глобальными. Не перенумеровывать реальные идентификаторы и не менять при этом порядок разрешения конфликтов.

Групповое правило связывает набор источников с набором целей. Удаление одной цели из такой группы влияет на все её источники: объяснить это до подтверждения. Разрыв только одной пары не должен молча удалять остальные связи; если нужна перестройка группы, показать конкретный результат и получить подтверждение. Новые противоречащие правила общей цели не создавать молча: показывать конфликт и фактический порядок действий, сохранять данные старых правил.

Для открываемого экземпляра доступно «Рукой и рычагами / Только рычагами». Во втором режиме ручной ПКМ даёт только этому игроку «не поддаётся», а рычаги продолжают работать. Настройка не применяется ко всем экземплярам типа и не подменяет RP Locked.

91094 — однократная анимация деревянных ворот: один допустимый запуск на ПКМ/импульс, без ложного устойчивого состояния открытия. 91088 в этой базе статичен. Новую анимацию/коллизию этим исключениям не придумывать; ранее отложенная переделка физики 91094 в это задание не входит.

8. ФОНАРИ 91063

Первичное связывание без меню:
— «Связать», ЛКМ по фонарю A — источник;
— ЛКМ по B — сохранить A↔B; по C — сохранить A↔C;
— регистрация узлов автоматическая, используются понятные временные имена и существующая либо автоматически созданная служебная линия;
— одинаковая пара повторным кликом не создаётся заново;
— на экране видны источник, имена назначений и направление.

A↔B и A↔C не создают B↔C. Меню «Телепорты» позволяет переименовать отдельный фонарь и линию, выбрать линию, изменить направление конкретной пары, убрать конкретную связь и удалить всю линию с отдельным подтверждением. Имя линии и имя фонаря — разные явно подписанные поля: не использовать поле имени фонаря для переименования линии.

По умолчанию связь двусторонняя; односторонний A→B задаётся явно. Если обратный путь существует по другой линии, показать это, а не объявлять B полностью без возврата. Режим «Разорвать» для фонарей по умолчанию удаляет выбранную двустороннюю пару в выбранной линии; одностороннее удаление доступно явно. Остальные линии/маршруты сохраняются.

Убрав инструмент, игрок обычным ПКМ по фонарю открывает меню назначений. Оно показывает имена фонарей, без технических названий линий/UUID, не приостанавливает игру, позволяет перейти и вернуться. Причины отсутствия назначений, задержки и отказа понятны. Для проверки обеих сторон реально пройти A→B→A, а не только прочитать граф.
Высота/поворот фонаря не разрывает его UUID-связи; разрушение удаляет соответствующие связи, новый экземпляр в тех же координатах их не наследует. Сохранить ограниченную загрузку дальнего назначения, безопасное прибытие и освобождение временных заявок при успехе/отказе/Esc/выходе. Не загружать мир постоянно ради сети или её графики. Исходный свет и респавн фонарей в этом задании не перерабатываются.

9. СОБЫТИЯ ОТКРЫТИЯ/ЗАКРЫТИЯ

Для настоящих открываемых экземпляров сохранить два отдельных упорядоченных списка команд: «После открытия» и «После закрытия». Редактор доступен только администратору уровня 4. Добавление/редактирование/удаление строки, перестановка и сохранение должны быть очевидными; показывать «Есть несохранённые изменения» / «Сохранено».

Событие принадлежит UUID конкретного экземпляра. Открытие, закрытие, поворот, монтажное смещение, переход на другой объект и повторный вход не стирают сохранённый список. Черновики разных объектов не смешиваются. Копирование/новая установка создаёт новый экземпляр без самовольного наследования связей/администраторских команд.

Команды исполняются от серверной консоли в контексте цели только после реального успешного изменения состояния: один раз, по порядку. Не исполнять их при редактировании, загрузке, обычной синхронизации и повторной установке уже имеющегося состояния. Если закрытие отложено, событие следует после фактического закрытия. Ошибка команды сообщается и журналируется, не откатывая успешное изменение объекта; сохранить защиту от рекурсивных цепочек.

Сохранить подстановки {id}, {uuid}, {x}, {y}, {z}, {dimension}, {player}. Owner UUID архитектуры не является UUID сущности для @e. Отсутствующий инициатор не подменяется случайным игроком; это явно объясняется. Неподдерживаемый статический/импульсный объект не должен получать выдуманные события устойчивого состояния.

10. ОСМОТР И ДИАГНОСТИКА

Разделить два понятных режима:
А) «Показать в мире»: область выбора, действующая коллизия игрока, корень/опорная точка, смещение, направление, связи. Коллизию и выбор рисовать по отдельности с подписью; декоративный габарит не выдавать за препятствие для игрока.
Б) «Записать отчёт»: снимок, ограниченная запись событий/нагрузки, остановка, пометка, экспорт.

Сохранить /bb debug и /bb diagnostics. /bb debug показывает тип/пятизначный ID, UUID, положение, ориентацию/высоту, поддерживаемые состояния и связи. Меню должно показывать ту же фактическую цель.

Запись выключена по умолчанию; простое открытие меню не запускает её. Кнопка записи на 60 секунд показывает область записи, оставшееся время и итог. Доступны весь мод, выбранный экземпляр и существующие фильтры, без размножения новых систем. «Снимок»/«Пометка» подтверждаются явно; ошибки не маскируются под успех.

После экспорта вывести в личный чат понятное имя и расположение файла. На локальном клиенте предложить «Открыть папку», если платформа позволяет, с безопасным подтверждением. На удалённом сервере отдельно сообщить серверный путь и локальный клиентский отчёт с общим номером сеанса; не обещать открыть серверный файл на компьютере игрока.

Показатели подписывать по-русски: клиентские кадры/FPS, серверный тик, измеренное CPU-время участков кода, память/сборка мусора, ошибки. GPU-время, которое не измеряется, обозначать «не измерено». Не вычислять выдуманный процент нагрузки конкретного блока из FPS. Сохранить пределы буферов, автоостановку, различие сторон и единого процесса встроенного сервера. Отчёты полезны вместе с графикой в игре и не заменяются одной подсветкой.

11. НАДЁЖНОСТЬ И ОПТИМИЗАЦИЯ

Истинные изменения — на сервере, после проверки прав, экземпляра, загруженности и допустимости. Клиент показывает подтверждённый результат и понятную ошибку/ожидание. При быстрых нажатиях, задержке сети и повторе пакета не создавать дубли, не терять сохранение и не менять другой объект. Запросы связывать с ожидаемым UUID/версией данных; ответы не должны перескакивать на новый выбор.

Выбор, рабочий источник связи, выбранная линия и черновик — разные сущности интерфейса. Источник не теряется при наведении на цель; завершение выбора не удаляет данные мира. Два игрока не делят один глобальный выбранный объект/черновик. Конкурентное изменение формы обнаруживается и предлагается перечитать, не затирая чужое сохранение.

Сохранить существующую UUID-совместимость, данные правил/фонарей/команд и различие удаления/выгрузки чанка. Миграции версионировать и проверять на копии старого мира. Массово не менять схемы хранения без необходимости.

Подсветка/линии — клиентские и ограниченные выбранным объектом/группой и видимой областью. Не сканировать каждый кадр весь мир/все чанки, не запрашивать полные списки всех правил постоянными пакетами. Кэшировать и обновлять нужные данные по изменениям; история отмены/журналы ограничены. Не создавать новую громоздкую тестовую инфраструктуру, если достаточно существующих средств.

12. ДОПОЛНИТЕЛЬНЫЕ ПРАВКИ ОБЪЕКТОВ И КАРТА-ГАЛЕРЕЯ

Выполни этот раздел после исправления инструмента. Все требования ниже входят в это же задание и в итоговую сборку. Они уточняют только отмеченные свойства; остальные свойства объектов сохранить.

12.1. ОГРАДА ИЗ ПОЛИРОВАННОГО ГЛУБИННОГО СЛАНЦА: 90002 И 90012

Оставить ровно два пользовательских варианта этой ограды:
— 90002 — обычная соединяющаяся ограда;
— 90012 — отдельный диагональный столб без соединений.

Варианты 90013, 90014, 90015, 90016 и 90017 удалить из доступного каталога, Creative, рецептов, выдачи и меню инструмента. Удалить их самостоятельные реализации и лишние ресурсы, если они больше никому не нужны. Не удалять общие ресурсы, используемые сохраняемыми объектами, и не присваивать выведенные номера другим типам.

90002:
— убрать установку и поворот под 45°; допускаются только обычные ортогональные направления;
— обычные соединения с подходящими соседями должны работать как у стандартной ограды Minecraft;
— блок должен нормально устанавливаться по штатным правилам оград, в том числе без опоры снизу;
— отсутствие, удаление или изменение блока под ним не должно ломать ограду, удалять её, превращать в предмет или запрещать уже допустимую установку;
— не менять не относящиеся к этим исправлениям материал, оформление и согласованную игровую коллизию.

90012:
— установка и поворот разрешены ТОЛЬКО по диагонали: 45°, 135°, 225° и 315° относительно осей мира; 0°, 90°, 180° и 270° недоступны как при установке, так и через инструмент;
— всегда сохраняется оригинальная форма самостоятельного «столба»: соседние блоки не добавляют перекладины/ответвления, не заменяют модель и не меняют её соединяемый вариант;
— взаимное соединение отключено: 90012 не соединяется с соседями, а обычные и модовые ограды, стены, панели и другие соединяемые блоки не должны добавлять соединение именно из-за соседства с 90012;
— это не отключает нормальные соединения соседних блоков с другими подходящими объектами и не отменяет их обычные обновления;
— правила установки/соседние обновления/сохранение/загрузка и кнопки 90009 не должны обходить ограничения угла или возвращать соединяемый визуал. Не предлагать режим оформления, нарушающий постоянную форму столба.

В дальнейшем для новых оград использовать этот же принцип: два варианта, обычный соединяемый и только диагональный без соединений в обе стороны. Зафиксировать правило в документации проекта и в общей реализации там, где это уместно. Новые виды оград в рамках этого задания не добавлять и исправные существующие виды без отдельного требования не переделывать.

Совместимость удаления вариантов: не уничтожать размещённые объекты и не делать старые сохранения нечитаемыми. Предусмотреть совместимый переход 90013–90017 к 90002 либо 90012 по фактическому старому назначению/углу, а для старых недопустимых установок 90002/90012 — явное правило перехода к соответствующему сохраняемому варианту. Сохранять положение и совместимые данные экземпляра. Скрытый технический алиас допустим только для чтения/миграции старых данных, без самостоятельного пользовательского варианта; после перехода использовать актуальный тип. Не сканировать принудительно весь мир. В отчёте привести точное соответствие старых и новых ID/состояний. Этот же принцип безопасного удаления применяется к 90018/90019 ниже.

12.2. 90003: РАЗМЕЩЕНИЕ ЛЮБЫХ БЛОКОВ В ПЕРЕСЕКАЮЩЕЙСЯ ОБЛАСТИ

Для 90003 убрать запрет установки любых обычных и модовых блоков вокруг него и внутри области его геометрии/коллизии. Сейчас исключение допускает лишь его копии; расширить именно исключение для размещения блоков, по принципу уже реализованного разрешения пересечения у энтити-блоков.

Пересечение с 90003 само по себе не должно отменять установку блока, уничтожать/сдвигать 90003 или автоматически взаимодействовать с ним. Это касается только размещаемых блоков: не отключать заодно проверки размещения игроков, мобов и произвольных сущностей. Сохранить игровую коллизию 90003 для игрока, проверки прав, границ мира и реально занятых ячеек/инвентарей. Если 90003 имеет настоящий корневой блок, речь о разрешении пересечения с его выступающей областью, а не о безусловной перезаписи занятой корневой ячейки. Не разрешать размещение вопреки препятствиям, создаваемым другими объектами.

12.3. УБРАТЬ НАДПИСИ НАД ЭНТИТИ-БЛОКАМИ

У всех энтити-блоков убрать визуальные имена, названия, ID и аналогичные подписи над объектом, появившиеся в v10. Проверить обычное отображение, наведение прицела и выбор инструментом: такие надписи не должны появляться. В дальнейшем не создавать их для энтити-блоков; закрепить это правило в рендерере/общем поведении и документации.

Изменяется только отображение над объектом. Не удалять названия из каталога, предметов, меню, HUD, диагностических отчётов, данных экземпляра и механики именования фонарей. Не стирать CustomName/идентификаторы, если они нужны сохранениям или логике. Подсветка, линии связи и панель инструмента остаются; сведения об объекте показываются в панели/меню. Этот пункт не требует менять имена обычных мобов/NPC.

12.4. ЛЕСТНИЦА 90006 И УДАЛЕНИЕ ЕЁ КОПИЙ

Для 90006 изменить только проблемную коллизию при установке под 45°:
— при отсутствии опорных блоков должна быть корректная коллизия для игрока, согласованная с положением лестницы и позволяющая нормально пользоваться подъёмом;

— при добавлении/удалении опоры актуальное состояние должно пересчитываться без необходимости вручную переставлять лестницу. Опору определять по фактическому монтажу и соответствующим блокам, а не по наличию любой декорации поблизости.

Не включать сплошную коллизию всем лестницам или всем положениям 90006. Сохранить прочие рабочие варианты установки, подъём/спуск, модель, анимации и настройки; случаи, не обозначенные выше, не переделывать. Коллизия, монтаж и синхронизация должны сохранять правильное состояние после поворота/смещения инструментом и перезагрузки мира.

Копии 90018 и 90019 удалить из доступного каталога и пользовательских способов получения. Сохранить единственную лестницу 90006; обеспечить переход старых экземпляров/предметов к ней с сохранением совместимого положения и настроек по принципу раздела 12.1. ID не переиспользовать. 91069/91086 и другие лестницы этим пунктом не изменять.

12.5. ВОССТАНОВИТЬ ОТЛИЧАЮЩИЙСЯ ВИЗУАЛ 90020

В v10 тонкие остекления 90010 и 90020 визуально одинаковы. Ранее существовал третий отличающийся визуал тонкого остекления; найди его в истории репозитория/старых ревизиях мода, начиная со сравнения v9 и предшествующих изменений ресурсов. Восстанови этот прежний визуал для 90020 вместо дубликата 90010, включая нужные модель и текстуры/ссылки на них.

Не придумывать новый внешний вид и не подменять 90020 случайной похожей моделью. Зафиксировать, из какого коммита/ревизии и файлов взят восстановленный визуал. Если исходник действительно отсутствует во всей доступной истории и выдачах, указать конкретный недостающий ресурс, продолжить независимые исправления и не объявлять этот пункт выполненным.

В результате 90004/90010/90020 должны представлять три прежних самостоятельных визуала. Не менять ID/предмет 90020, монтаж «Вертикально / Пол / Потолок», ограничение поворота 90° и остальные исправные свойства. Проверить отсутствие пропавших текстур и правильное отображение во всех монтажных плоскостях, без исходного ресурс-пака и шейдеров.

12.6. КОРРЕКТНЫЕ ОБЛАСТИ НАВЕДЕНИЯ И ДОСЯГАЕМОСТЬ

Взаимодействие с блоками/энтити-блоками, включая использование и разрушение, должно срабатывать при наведении на их действующую коллизию игрока в пределах штатной досягаемости Minecraft для соответствующего типа цели и режима Survival/Creative. Сейчас у многих объектов область взаимодействия чрезмерно широкая: объект выбирается/ломается при прицеле на пустое место далеко от его реальной формы. В v9 это работало нормально — сравнить соответствующие формы выбора, хитбоксы, raycast и проверки дальности с v9 и найти регрессию.

Для объектов с коллизией игрока область обычного взаимодействия согласовать с этой коллизией: использовать реальные составляющие формы, а не один огромный охватывающий AABB, захватывающий пустоту между частями. Учитывать текущие поворот, высоту, монтаж и состояние открытия. Для объектов, у которых отсутствие коллизии игрока предусмотрено специально (например, поддержанная диагональная лестница), сохранить адекватную область выбора по их рабочей геометрии/v9; не делать их невыбираемыми и не добавлять физическое препятствие ради клика.

Не увеличивать глобальную дальность и не задавать одну произвольную константу всем блокам и сущностям. Проверить штатную клиентскую и серверную логику досягаемости, различия игровых режимов и препятствия между игроком и целью. Декоративная модель за пределами действующей формы не должна самовольно расширять обычную область разрушения.

Закреплённый выбор 90009 сохраняется по разделу 4. Если для удобного выбора инструментом необходима вспомогательная область/перебор кандидатов, ограничить это контекстом инструмента, не переиспользовать в обычном разрушении/использовании и не разрешать редактирование вне допустимой досягаемости. Не ломать согласованную физику игрока и живых сущностей ради исправления наведения.

12.7. ЗАПРЕТ ПОВТОРНОЙ АКТИВАЦИИ ДО КОНЦА АНИМАЦИИ

У всех интерактивных объектов, проигрывающих анимацию перехода состояния, запретить повторную активацию до фактического завершения текущей анимации. Сейчас повторное нажатие во время открытия прерывает его и начинает закрытие; это исправить. Аналогично нельзя прервать закрытие новым открытием или перезапустить однократную анимацию повторным нажатием.

Блокировка относится к конкретному экземпляру, а не ко всем объектам его типа. Сервер должен отклонять повторную активацию независимо от игрока, руки, удержания кнопки и повторов пакета; клиент показывает понятное состояние «анимация выполняется». Проверка должна охватывать все пути, способные повторно запустить/прервать этот переход, включая рычаги и предусмотренные программные действия. Не ограничиваться отключением одной кнопки GUI.

Продолжительность брать из фактической анимации/её серверного состояния, не подменять произвольной общей задержкой. После завершения новое взаимодействие снова доступно. Отклонённое действие не меняет целевое состояние, не перезапускает звук/анимацию и не исполняет события открытия/закрытия. Повторные клики не накапливать в очередь, неожиданно срабатывающую после разблокировки. Другие экземпляры остаются доступны.

Сохранить задержку рычагов 70 тиков, правильное исполнение групповых правил и уже предусмотренное безопасное отложенное закрытие. Согласовать их с состоянием занятости: не прерывать анимацию, не выдавать непринятое действие за выполненное и не дублировать события. Не добавлять вымышленные анимации статическим объектам. После выгрузки/загрузки или перезапуска экземпляр не должен навсегда оставаться заблокированным.

12.8. ПРАВИЛЬНОЕ РАЗМЕЩЕНИЕ 91030 И 91013

При обычной установке 91030 и 91013 сейчас утоплены в пол. Исправить их базовую опорную точку/смещение при размещении: нижняя опорная часть объекта должна корректно стоять на верхней поверхности блока, на который он устанавливается, без проваливания в него и без зависания.

Проверить предусмотренные повороты и сохранение после перезагрузки. Исправлять только эти два типа и соответствующую причину; не вводить общий компенсирующий сдвиг всех RP-объектов, не менять масштаб и не заставлять игрока вручную поднимать их после каждой установки. Ручное смещение высоты 90009 должно работать относительно исправленной базовой посадки; сброс возвращает эту правильную базу.

12.9. ГОТОВАЯ КАРТА-ГАЛЕРЕЯ ВСЕГО АКТУАЛЬНОГО КАТАЛОГА

Создать отдельный готовый мир Minecraft 1.20.1 с галереей всех актуальных блоков, энтити-блоков, предметов и NPC этого combined-мода после исправлений/удалений. Состав брать из фактических registries/каталога итоговой версии, а не из устаревшего списка v10. Включить рабочие типы, даже если они отсутствуют в Creative; внутренние технические прокси/части одного объекта не считать самостоятельными экспонатами. 90008, 90013–90017, 90018/90019 и скрытые миграционные типы не выставлять как доступные варианты.

Каждому актуальному типу/ID выделить отдельную подписанную платформу:
— размещаемый блок или энтити-блок установить реальным экземпляром;
— предмет, который не размещается как блок/энтити-блок, показать в рамке; предметы размещаемых блоков не требуют второй платформы-дубликата;
— NPC показать реальным представителем соответствующего типа, а не заменить одним яйцом призыва/муляжом. Экспонаты должны оставаться у своей площадки.

Размер платформы вычислять по горизонтальной проекции действующей коллизии игрока у выставленного объекта в его фактическом положении: площадка покрывает весь её габарит и добавляет по 2 полных блока с каждой из четырёх сторон. Границы округлять наружу до сетки блоков. Зазор между БЛИЖАЙШИМИ КРАЯМИ соседних платформ — 2 пустых блока; это не расстояние между центрами. При разных размерах платформ подбирать раскладку с этим зазором, без пересечений. Для экспоната без игровой коллизии использовать фактический визуальный габарит, для предмета в рамке — габарит экспозиции. Не использовать одну тесную одинаковую платформу для всех размеров и не включать прежние ошибочно раздутые области выбора в расчёт.

Подписи — название, пятизначный ID, при необходимости краткая особенность; использовать таблички/указатели, без возврата имён над энтити-блоками. Обеспечить освещение, удобный обход, понятный вход и навигацию по разделам. Первый вход — Creative, читы доступны, игрок появляется у начала галереи и получает 90009. Мир не должен требовать QA-мод, старый ресурс-пак, шейдеры или дополнительные обязательные моды сверх рабочего профиля итогового JAR.

В той же карте сделать компактный отдельный стенд проверяемых функций инструмента: связанные рычаги/двери, связанные фонари с возвратом, клетки с собаками, примеры монтажа/высоты, оба варианта ограды и обе описанные установки 90006. Этот стенд дополняет полный каталог, а не заменяет его выборкой примеров; соблюдать размеры/зазоры платформ и не заслонять экспонаты.

Перед выдачей сверить выставленные ID с итоговым каталогом: ноль пропущенных актуальных типов экспонатов, ноль лишних удалённых типов; привести количества блоков, предметов и NPC. Открыть и пересохранить мир с точным итоговым JAR, проверить сохранение экспонатов/связей и правильный вход. Выдать ZIP полноценного мира с level.dat, чанками, данными сущностей и необходимыми данными мода; одного генератора, списка команд, схематики или инструкции «создайте мир сами» недостаточно. Сохранить использованный генератор/сценарий в исходниках, если он был создан, для дальнейшего воспроизведения галереи.

13. ОБЯЗАТЕЛЬНЫЕ КОМПЛЕКСНЫЕ ТЕСТЫ

Работа не считается завершённой по наличию кода, успешной компиляции или списку кнопок. Обязательно проверить реальное поведение всех перечисленных функций и отсутствие регрессий затронутых объектов.

Перед исправлениями кратко воспроизвести жалобы на копии исходной v10. Для каждого воспроизведённого дефекта — причина, изменение и проверка после исправления. Подготовить проверочную таблицу «действие пользователя → ожидаемый результат → наблюдённый результат → сборка/среда → доказательство». Для всех типов составить перечень настоящих возможностей; отдельно проверить каждый особый обработчик. Общую механику проверять на представителях каждой реализации, без бессмысленного перебора всех сочетаний декоративных состояний.
