# Интеграция Bloodborne RP

Использован предоставленный `bloodborne-rp-1.0.0-rp.2-full-source.zip`, а не публичный пакет с резервной графикой. Java-код находится отдельно в `src/rp/java`, ресурсы — в `src/rp/resources`, исходные тесты — в `src/rp/tests`. Импорт воспроизводит `tools/import_rp.py`; каждый исходный ZIP entry и SHA-256 записан в `reports/RP_IMPORT.json`.

Первоначальный импорт сохранил 30 Java-файлов основного RP без правок. Независимая проверка source-author V3 обнаружила потерю неизвестных Forge NBT при игровом сохранении; в текущей интеграции изменены только RpObjectEntity и RpMobEntity, добавлен helper SourceLegacyPayload. Остальные 28 исходных файлов и все 707 ресурсов побайтно прежние. Точные хеши и diff находятся в reports/RP_SOURCE_INTEGRATION.json и reports/RP_SOURCE_INTEGRATION.patch. Сравнение с `origin/bloodborne` подтвердило совпадение кода отдельного RP и RP в старом Complete: 42 побайтовых совпадения и 18 совпадений текста с различающимися окончаниями строк. Копирования старой архитектуры Complete не было.

Полный набор получается наложением `private-assets` из предоставленного ZIP на исходные ресурсы RP. 707 файлов ресурса и его manifest побайтово совпадают с предоставленным `bloodborne-rp-1.0.0-rp.2-full-local.jar`. Проверены 306 ссылок каталога на геометрию, PNG и анимации и 293 ссылки на клипы. Ни одна геометрия каталога не ссылается на fallback. 64 статические записи без клипов намеренно используют общий `fallback.animation.json`; этот служебный выбор уже есть в полном RP и не заменяет оригинальную геометрию. Файловая проверка ресурсов отделена от клиентской приёмки фактического рендера; её свидетельства и ограничения фиксируются в клиентских отчётах.

## Сохранённые контракты

| Контракт | Состояние |
|---|---|
| Namespace | `bloodborne_rp`, без переименования |
| Главная точка входа | `dev.dreamwalker.bloodbornerp.BloodborneRp`, один вызов в объединённом metadata |
| Клиентская точка входа | `dev.dreamwalker.bloodbornerp.client.BloodborneRpClient` |
| Registry | 18 мобов, 76 entity-объектов, 94 entity types, 98 item types, 0 RP-блоков |
| Оружие | `saw_cleaver`, `saw_spear`, `boom_hammer`; две формы одного ItemStack |
| NBT оружия | `BloodborneRpForm`, `BloodborneRpWeaponProfile`, сохранённые чужие AttributeModifiers |
| NBT объектов | UUID, Pos, Rotation; Open, Locked, Scale, Links, ConnectionId, LeverPulseTicks |
| Состояние мобов | стандартные Health/Attributes/Brain через superclass, существующий `bloodborne_rp_frozen` |
| Конфигурация | `config/bloodborne-rp.json`, существующая схема |
| Команды | `/bbrp object ...`, `/bbrp lamp ...`, без конфликта с архитектурными `/bb` и `/bloodborne` |
| Фонари | `data/bloodborne_rp_lamps.dat`, Schema=1; Id, Lamp, Name, Dimension, packed Pos и направленные Routes |

Установка использует один объединённый `dreamwalker-bb-fabric-1.20.1` JAR с mod ID `bloodborne_dw` и `provides bloodborne_rp`. Отдельный Bloodborne-RP и старый Complete заменяются этим JAR. GeckoLib 4.4.9 уже включает mclib 20; отдельный mclib не требуется. RP-код не импортирует mclib напрямую.

Проверка первого конечного JAR выявила реальную ошибку metadata: одновременно `provides bloodborne_rp` и `breaks bloodborne_rp:*` запрещают мод самому себе под Loader 0.17.2. Наличие исходного namespace не является конфликтом: его регистрацию вызывает ровно одна главная точка входа. Ошибка исправляется в объединённом metadata; первый отрицательный запуск сохранён как свидетельство в `build/runtime-server-minimal-first/launch-console.log`.

Дополнительная проверка установки выявила, что Loader 0.19.5 может молча исключить отдельный RP из resolved mods из-за `provides bloodborne_rp`. Поэтому проверка только `getAllMods()` не обнаруживала лишний JAR: первый целевой отрицательный тест честно имеет FAIL в `reports/SERVER_NEGATIVE_STANDALONE_RP_BEFORE_GUARD.json`. Исправленный архитектурный `preLaunch` проверяет точный `id` в корневом `fabric.mod.json` включённых JAR папки mods и выдаёт сообщение с фактическим путём конфликтующего файла. Подлинный предоставленный standalone RP вместе с актуальным объединённым JAR теперь имеет **PASS_INCOMPATIBLE_INSTALL_REJECTED**: код выхода 1, стадия preLaunch, сообщение `Remove standalone bloodborne-rp.jar before starting.`, ноль RP-инициализаций, отсутствие duplicate registry error. Свидетельства находятся в `reports/SERVER_NEGATIVE_STANDALONE_RP.json` и `build/runtime-server-incompatible-standalone-rp-prelaunch/launch-console.log`; тогда исходные RP Java-файлы ещё не были изменены.

## Forge NBT и лампы

Исторический `complete_convert_world.py` нельзя применять: он глобально переписывал compound `id`, удалял Health/Attributes/Brain/ForgeCaps и принудительно замораживал мобов. Новый `tools/rp_migration.py` использует типизированные NBT и конкретный контекст entity, ItemStack, player inventory или block entity inventory. Имена registry сверяются с реальным каталогом и исходной регистрацией. Неизвестный Forge ID сохраняется и попадает в отчёт; произвольные строки, Lore, ForgeCaps и посторонние compound `id` остаются нетронутыми. Известные формы старого оружия сводятся к существующему семейному предмету с сохранением формы в `BloodborneRpForm`. Противоречивые состояния имеют явную ошибку и не перезаписываются.

Исходная карта содержит 60 типов Forge RP-сущностей; все соответствуют существующим RP entity registry IDs. Две пары ворот уже открыты (`EntityState=1`); исходный RP-порт прямо читает такое состояние для `main_gate` и `small_gate`, поэтому его не нужно угадывать или обнулять. Данные шести рычагов и связанных ворот описаны в `reports/RP_MIGRATION_PLAN.json`. Существующий код восстанавливает связи по ConnectionId при действии рычага; фактические пары и сохранение после игры ещё требуют проверки.

В карте есть `data/hunter_lamp_manager.dat` с **двумя одинаковыми** регистрациями единственного фонаря, а не готовый `bloodborne_rp_lamps.dat`. Фонарь находится в Overworld, `(229, 69, -931)`. Его исходный пользовательский `Id` и стандартный entity UUID различаются. Проверенный план сохраняет исходный Id как `Node.Id`, UUID сущности как `Node.Lamp`, имя area и координаты; dimension выводится по реально найденной сущности. Точная дублирующая запись учитывается как исходный дефект. Направленных маршрутов в исходных данных нет: функция не создаёт сеть путешествий. Оригинальный legacy dat сохраняется; новый RP dat должен быть отдельным результатом миграции. Регистрация существующей сущности в маршрутах не доказывается одним её присутствием в мире.

12 регрессионных тестов проверяют сохранение UUID/Health/Attributes/Brain/ForgeCaps, механизмов, отказ неизвестных IDs, вложенные контексты, оружие, повторный запуск и разные идентификаторы фонаря с отсутствием выдуманных маршрутов. `audit_rp_migration.py` независимо сравнил все типизированные поля оригинала и кандидатного результата в 264 entity contexts (262 RP), шести player snapshots и 56 inventories block entities. Все изменения ограничены явным журналом, повторная миграция этих записей ничего не меняет. 180 встреченных предметов Forge для рычагов/ворот/дверей получают проверенные RP `_placer` ID.

Общий dry-run остаётся **FAIL / NOT_APPLIED**, поскольку восемь утилитарных предметов ещё не имеют соответствия: `bloodborne:delete` — четыре, `bloodborne:shrink` и `bloodborne:enlarge` — по два. Они сохранены исходными, без произвольной замены. Совместимые инструменты либо согласованный адресный перенос их функций нужны до финальной игровой загрузки соответствующих инвентарей. В относящихся к RP данных обнаружены также три исходных entity region-файла короче заголовка и один повреждённый временный `.dat`; они записаны отдельно как исходные дефекты. Полный WORLD_AUDIT учитывает 13 дефектов исходных файлов.

Офлайн сохранность проверяется отдельно от настоящего игрового save. Исторический source-author V3 имеет независимый FAIL: RP удалял AnimationId/EntityState/CanUpdate/IsActivated/Id и другие необработанные поля. Исторический source-author V4 на подготовке V6 уже прошёл независимую проверку всех 15 UUID/registry IDs, полного типизированного SourceLegacyPayload.Original и неизвестных полей верхнего уровня; `reports/SOURCE_REVIEW_POSTSAVE_INDEPENDENT_V4.json` остаётся свидетельством именно той сборки и содержит 1324 metadata/DFU/таймерных различия.

Исторический source-author V7 и повторное открытие с production JAR `1c9e2788c79223072e89150c2fdbef159e6e226bb76a823cd1296ba9e43027f9` отдельно проверены в `reports/SOURCE_REVIEW_POSTSAVE_INDEPENDENT_V7.json` и `reports/SOURCE_REVIEW_POSTSAVE_REOPEN_INDEPENDENT_V7.json`: все 15 RP UUID/registry IDs, полный типизированный SourceLegacyPayload.Original и неизвестные поля верхнего уровня сохранены; ошибок payload, незапланированных изменений native nonmembers и foreign block entities — ноль. Оба адресно перенесённых технических light-блока остаются с исходной семантикой light9 и пустыми collision/selection. Подготовка остаётся неизменной V6. Первое сохранение V7 отдельно записало 1157 различий metadata чанков и 4363 дополнительно созданных чанка; они не объявляются равными исходнику. Повторный replay проверяет прежние UUID/footprint и идемпотентность в `reports/SOURCE_REVIEW_PERSISTED_REPLAY_INDEPENDENT_V7.json`.

Envelope хранит типизированный вход после явно журналируемого offline ID mapping; исходные Forge bytes дополнительно остаются в неизменённом архиве. Текущие role writers и vanilla Health/AI/position имеют приоритет, поэтому сохранность не замораживает здоровье или поведение. Повторное чтение/запись не увеличивает вложенность envelope. Полный сохранённый мир и все живые vanilla NBT не объявляются побайтно одинаковыми. Массовая миграция города ещё не выполнена; файл содержит план и чистые функции для следующего принятого этапа. `reports/RP_MIGRATION_DRYRUN.json` сохраняет пути всех записей, хеши до/после, состояние lamp candidate и адресные ошибки.

## Сборка и совместимость

Исходная сборка RP: Minecraft 1.20.1, Java 17, Loom 1.6.12, Yarn `1.20.1+build.10:v2`, Loader 0.16.10, Fabric API `0.92.9+1.20.1`, GeckoLib 4.4.9. Рабочий Java 17.0.15 найден в `java-runtime-gamma` установленного Minecraft; версия `java` и `javac` проверена. Системный java в PATH — Java 21 и для этих запусков не используется.

Проверка зависимостей на настоящем Loader показала: Create требует минимум 0.17.2, а Farmer's Delight 2.5.7 вместе с вложенным PortingLib 2.3.15 — минимум 0.18.2. В действующей установке пользователя подтверждён **Loader 0.19.5**: metadata файла `dw/0.19.5.jar` и строка Loading Minecraft из `logs/latest.log` совпадают. Поэтому воспроизводимый профиль использует именно существующий 0.19.5; это не произвольное обновление. Исторические промежуточные проверки на 0.17.2 и 0.18.2 сохранены с отдельными версиями и хешами JAR. Compile baseline 0.16.10 не меняется.

`mods.zip` содержит 122 основных JAR и 530 вложенных JAR; metadata и хеши находятся в `reports/MODSET_INVENTORY.json`. Архив содержит 12 пар дублирующих mod ID. `reports/MODSET_PROFILE.json` явно выбирает 109 файлов и исключает 13 (12 дублей и заменяемый standalone RP). Для единственной установленной версии используется её точный SHA-256; рендерный набор выбирается совместно из предоставленных Sodium 0.5.13, Iris 1.7.6, Indium 1.0.36 и стабильного Continuity. Fabric API остаётся 0.92.9. Файлы установки пользователя не меняются. Строгий JSON-парсер обнаружил управляющий символ в metadata CameraOverhaul; этот факт записан, и окончательное поведение проверяет настоящий Fabric Loader.

`tools/run_final_server.py` создаёт отдельную новую плоскую тестовую карту, копирует конечный remapped JAR и только выбранные зависимости, связывает сервер с `127.0.0.1` и случайным локальным портом. Явные generator-settings содержат plains и 128 слоёв bedrock/dirt/grass с поверхностью на Y=63; прежняя ошибка пустых layers устранена на новой карте. Официальный endpoint Fabric задаёт библиотеки выбранного Loader с проверкой предоставленных SHA-256. Launcher использует явный classpath: экспериментальный manifest-only launcher под 0.17.2 создавал ошибку изоляции классов и не используется. EULA берётся из уже принятого файла прежнего независимого теста с фиксацией пути и хеша; инструмент сам не принимает соглашение. Исходная карта и рабочий сервер не загружаются. Результаты запусков находятся в `reports/SERVER_MINIMAL.json` и `reports/SERVER_FULL_SERVER.json`; предыдущие свидетельства до preLaunch исправления сохранены отдельно в `*_BEFORE_GUARD.json`. Отрицательная установка допускается только явными `--extra-mod`, `--expect-rejection` и отдельным `--report`.

Исторический checkpoint prototype.1 JAR `a85a8a4c98aac7422b6b02e7fe19373a648c31a910101018c18100eab49f03c6` повторно прошёл файловую RP-проверку и оба обычных dedicated запуска на **Java 17 / Loader 0.19.5**. Минимальный профиль: 39.719 секунды до Done, одна RP-инициализация, ноль ERROR, штатные сохранение и выход 0; `build/runtime-server-ladder-scene-prelaunch-final/launch-console.log`. Все команды `tools/prototype_scene_commands.json` выполнены: 12 экземпляров лестницы (четыре направления × три варианта), vanilla контрольные блоки, RP tree1 и hunterlamp, Creative, фиксированный spawnRadius=0 и worldspawn=(-2,64,0), save-all flush. Отдельная нормально сохранённая контрольная карта находится в `build/runtime-server-ladder-scene-prelaunch-final/isolated-smoke-world`.

Профиль с **83 выбранными server-compatible по metadata модами**: 101.281 секунды до Done, одна RP-инициализация, сохранение восьми созданных dimensions, остановка с кодом 0; `build/runtime-server-full-profile-prelaunch-final/launch-console.log`. В полном журнале остаются 103 ERROR от других модов (datafixers, KubeJS, Chisels&Bits и др.); ошибка No key layers отсутствует. Статус PASS относится к startup/save/shutdown этого профиля; полная игровая совместимость имеет статус **NOT_ACCEPTED**. Время зафиксировано во время соседних изолированных QA-процессов и не является измерением производительности города. Если JAR меняется, эти свидетельства не переносятся на новую версию автоматически. Успешный пустой сервер не считается визуальной приёмкой, проверкой боевой системы или нагрузкой города.

`tools/run_final_client.py` готовит отдельный обычный игровой профиль с тем же конечным JAR и выбранным набором модов. Используются Java 17, правильные Windows AMD64 natives и публичные официальные библиотеки. `tools/ensure_client_assets.py` проверил точный asset index5 SHA1 `c8035a2d33a185b89644c37f1fb98e5d0120273d` и все 3575 уникальных объектов в отдельном build-кэше; старые индексы с другими SHA не выдаются за совпадающие. Учётная запись для локальной QA — `DreamwalkerQA` с literal offline token `0`; реальные аккаунты и launcher credentials не читаются. Подготовка сама не запускает игру; `--launch` используется для отдельной разрешённой игровой проверки. Источники библиотек, хеши, profile и JAR записываются в клиентских отчётах.

Общие инструкции Fabric по dedicated-серверу: [Fabric Wiki](https://wiki.fabricmc.net/player:tutorials:server:windows). Использованный version-specific metadata endpoint: [Loader 0.19.5 / Minecraft 1.20.1](https://meta.fabricmc.net/v2/versions/loader/1.20.1/0.19.5/server/json).

Предыдущий проверенный prototype.2 JAR имеет SHA256 `14e88d539224121cbdcb7037b38c50cb64dc3edc52fe6028dfbc21aba3b2eeb6`; его отчёты V4 сохранены как история. Файловый reports/RP_PACKAGE_VERIFICATION_FIRST_SET_FINAL.json подтверждает прежние 707 RP-ресурсов, 306 ссылок каталога и 293 клипа. QA-addon проверяется отдельно и отсутствует в production JAR. Обычный минимальный профиль успешно авторизовал новую сцену 68 объектов и ограниченную исходную сцену 41 объект; оба запуска сохранились и завершились кодом 0. Реальные отчёты: SERVER_REVIEW_SCENE_AUTHOR_V4.json и SERVER_SOURCE_REVIEW_AUTHOR_V4.json. Полная игровая совместимость сборки и пользовательская приёмка первого набора остаются отдельными незавершёнными проверками; исторический full-server startup не переносится на новую версию.
