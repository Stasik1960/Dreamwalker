Этот план выполнен: **22/22 случая PASS** на production SHA
`baaf38ab7449c2336dff7f882ee26677002b99b046238160f5d8b8d87e23ddf6`.
Финальный отчёт `build/v12-delivery/native-acceptance.json` завершён

Реальные действия клиента, GUI, два игрока и rejoin дополнены сохранённым NBT
и GameTest для отдельных утверждений C2/P2/D2. Это не непрерывный видеопроход,
FPS или полная визуальная приёмка каталога. Ниже сохранён порядок плана;
его исходный JSON PREPARED не является текущим статусом. Предыдущие проверки
V11.3 не повторялись целиком.
Сборки, серверы, миры и клиенты запускаются через `Guard.ps1 -Mode Operation`;
рабочее хранилище C:, старые релизы и исходные миры сохраняются неизменными.

После сборки root: `tools/build_v11_gallery.py --revision V12 --jar <production>
--qa-jar <gallery-QA> --accepted-eula-file <accepted> --output build/v12-gallery-final
--run-name v12-gallery-final`. Автор создаёт новый мир, затем проверяет сохранённые
NBT и открывает/сохраняет его только с production JAR. Ожидается 121 экспонат:
103 предлагаемых предмета, включая одну рамку `bloodborne_dw:bb_tool`, и 18 NPC.
Ожидание уточняется по фактическому текущему каталогу, а не подменяется вручную.

Для игровых случаев нужна отдельная свежая копия сохранённого мира с небольшой
проверочной зоной: дверь, 7 рычагов, 2 фонаря, клетка с собакой, два объекта одного
ID внутри выбранного радиуса и третий за его пределами, обычная и угловая90006.

Проверять C3 удобно до запуска второго окна: A выполняет свои действия, затем
запускается B и остаётся единственным foreground-окном. Background A не активируется
через Sky; он может только читать состояние/делать родные ScreenshotRecorder кадры.
Повторный заход выполняется штатным закрытием и свежим запуском того же сохранения,
без перезаписи исходного fixture. Не требуется новый долгий benchmark для неизменной
сцены: второй настоящий клиент нужен для синхронизации и личного/общего лимита.

Доказательства: native F2 GUI/чат, небольшой ScreenshotRecorder batch для
предварительного и конечного состояния, vanilla `data get entity <UUID>` для
`Pos/Open/Locked/DogsVisible`, scoreboard/storage счётчики нейтральных тестовых
команд, saved NBT до/после reopen. Query не считается нажатием инструмента.

Существующие Java QA API: `RpObjectEntity.isOpen/animationBusy/dogsVisible/verticalOffset`,
`MechanismRules.list/rule/flag`, `MechanismLinks.targets/sources/inspect`,
`ObjectPolicies.leversOnly/commands` и `LampState` saved-state. Assertions проверяют
состояние после настоящего действия/публичной production операции; прямое создание
правила не доказывает работу ЛКМ. Новые command-limit поля утверждаются только через
реальный API новой реализации, не через придуманные имена NBT.

`run_v11_client.py` уже готовит отдельные offline UUID/имена, localhost quickPlay,
свежие fixture-копии, F8(use)/F9(attack) по опции `--qa-keybindings`, pinned Java17,
maxfps30 и SHA-bound QA marker. `run_v11_server.py` поддерживает mailbox, hold и
normal-stop; пользовательские файлы/учётные записи не изменяются. `--launch` и live
commands выполняет root. Capture-addon не делает tool clicks и ждёт закрытия GUI;
для console GUI используются обычные native F2 кадры, а не фиктивный camera PASS.

Минимальный результат: production SHA, 121-сводка галереи, результаты новых
контрактных проверок, 10–20 осмысленных native кадров, таблица случаев с factual
PASS/FAIL/PENDING и сохранение/rejoin. Старые сотни PNG и полные логи не копируются
в новый пакет. Любая поправка JAR инвалидирует SHA-bound выводы изменённого случая.
