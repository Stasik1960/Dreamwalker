# Приёмка и публикация V12.7

Эта страница описывает условия; она не является результатом проверки.
Родительский исполнитель создаёт `acceptance.json` после финальной сборки и
настоящих клиентских/серверных проверок. Порядок: промежуточный commit исходников,
сборка combined JAR, итоговые тесты, принятие доказательств, упаковка, публикация.
При последующем изменении исходников, JAR или принятого доказательства приёмка
и соответствующие проверки обновляются. Ранние FAIL сохраняются как история.

Упаковщик `tools/package_v127_release.py` ожидает JSON:

Перед упаковкой `tools/record_v127_acceptance.py` получает явные пути к
финальным доказательствам. Он ничего не запускает и не ищет «последний» отчёт.
`--validate-only` проверяет входы без записи acceptance. Полный перечень
обязательных аргументов выводит `--help`; `--counts` содержит окончательные
неотрицательные целые числа, утверждённые родительским исполнителем. Нативные
клиент/сервер/конвертер, resource-аудит и pixel-review обязаны сами содержать
SHA final JAR; ручная аттестация вместо этого запрещена.

Статические доказательства и GameTests devclasses без поля JAR SHA получают
точную аттестацию `--proof-bindings`: `status=PASS_FINAL_FROZEN_PROOF_BINDINGS`,
`productionJarSha256`, `sourceCheckpoint`, пустой `currentUnresolvedTestFailures`
и `proofs`. В `proofs` ключ — путь доказательства относительно проекта; значение
содержит его `sha256`, тот же `productionJarSha256` и `sourceCheckpoint`.
Перечисляются все входные статические/dev-доказательства без собственного поля
JAR SHA, включая native XML. GameTests JSON дополнительно содержит точный
`sourceCommit`; XML проверяется на реальные testcase, нулевые
failure/error/skipped. Это явная привязка замороженного запуска и исходников,
а не разрешение считать старые native-отчёты текущими.

Неполный/подготовленный отчёт, текущий FAIL, старый SHA, непроверенная исходная
схема, изменённые исходники или pending-политика блокируют запись. Старый
acceptance не перезаписывается автоматически. SQLite проверяется по SHA и
поставляется в conversion ZIP, без второй лишней копии в verification ZIP.

- `status: "PASS"`, точный `productionJarSha256`, `productionSourceCheckpoint`,
  `baselineCommit`, итоговые `counts` и пустой `currentUnresolvedTestFailures`.
- `evidence`: именованные записи с `path` относительно проекта либо локальным
  абсолютным путём в нём и `sha256`; при упаковке каждый файл проверяется снова.
- `checks`: отдельные PASS для `build`, `gameTests`, `nativeClient`,
  `nativeServerSaveReopen`, `resources`, `manualPlacement`, `worldEdit`,
  `fullConversionPlan`. Специальные пределы проверки отражаются в значении и
  содержимом доказательства, а не скрываются за общей успешной сборкой.
- `checks.physicalMouseKeyboard: "NOT_RUN"`; GUI Blockbench также NOT_RUN, если
  действительно не запускался. `fullOriginalWorldConverted: false` и
  `authorCollisionExport: "NOT_SUPPLIED_NOT_APPLIED"`.

Тест маленького автономного потока конвертации может быть PASS, тогда как
полный оригинальный мир остаётся PREPARE_ONLY/NOT_RUN по указанию владельца.
`fullConversionPlan=PASS` означает отсутствие неразрешённых видимых исходных
ячеек, привязанный поток/исполняемый путь и проверенную маленькую копию;
он не означает уже конвертированную оригинальную карту.

`tools/validate_v127_conversion_fixture.py` читает настоящие Anvil/NBT после
author и чистого повторного открытия производственным модом. Он проверяет
фактическое пересечение сохранённых физических призм, исходные типизированные
RP-поля, UUID/позицию/поворот и состояние/геометрию словарных shard. При сравнении
сущности исключены только изменяемые ванильные счётчики `Air`, `Fire`,
`PortalCooldown`, `FallDistance`, `OnGround`, `TicksFrozen`; пользовательские
поля, ссылки и непрозрачное исходное содержимое остаются точными. Присутствие
одного поля без проверки содержимого не является доказательством сохранности.

Малая проверка исходной схемы должна использовать
`prepare_v127_conversion_fixture.py --original-level-template`: только
оригинальный `level.dat` из ZIP с правильным SHA и новый чанк версии 2975.
Нативный author и последующее чистое открытие обязаны обновить сохранённый
уровень до версии 3465 или выше. Старый тест со схемой плоского мира сохраняет
свой PASS, но получает `NOT_RUN_ORIGINAL_SCHEMA` для этой отдельной проверки.

Окончательный полный план обязан включать одобренное сохранение 9 481 301
исходной клетки снятых типов: видимые поверхности через скрытую совместимость,
подходящие ванильные наполнители только в доказанно закрытых непрозрачных кубах.
Статус политики `APPROVED_PENDING_IMPLEMENTATION`, старое удаление всей группы
и `runtimeExecution`, начинающийся с `BLOCKED`/`PENDING`, блокируют приёмку и
исполнение даже при наличии прежнего `PASS_COMPLETE_SOURCE_PLAN`. Итоговая
политика, SQLite, runtime manifest и подготовленная копия связаны точными SHA.
`fixtureOnly=true` никогда не принимается за полный оригинальный план.

Нативные проверки освещения/opacity, WorldEdit и хранения состояний/владельцев
предъявляются отдельно. Статические результаты и размер NBT не заменяют
сравнимую память процесса либо осмотр полного города после пересчёта освещения.
Python-подготовка официального сервера через
`tools/prepare_v127_server_bootstrap.py` не запускает Java. Будущий runner
использует `--server-bootstrap build/v127-server-bootstrap` и launcher из
этой папки; `JAVA_HOME17` имеет приоритет над `JAVA_HOME`.

Финальный Blockbench ZIP сверяется с `visual-export/final-delivery-audit.json`.
Runtime plan требует `PASS_COMPLETE_SOURCE_PLAN`, ноль известных видимых gaps,
оба исходных SHA и правильные контрольные суммы всех потоков. Исходные ZIP
повторно хэшируются. Все архивы читаются потоками; проверяются CRC и SHA каждой
записи. Папка `releases/Dreamwalker-BB/v12.7-final` создаётся один раз; прежние
релизы и промежуточная папка после ошибки не перезаписываются и не удаляются.

```text
python tools/package_v127_release.py --runtime-plan build/v127-runtime-conversion-final2 --source-plan build/v127-full-conversion-first.sqlite --validate-only
python tools/package_v127_release.py --runtime-plan build/v127-runtime-conversion-final2 --source-plan build/v127-full-conversion-first.sqlite
python tools/publish_v127_release.py
```

Последняя команда по умолчанию выполняет только preflight. Публикация уже
разрешена владельцем в задании, но запускается родительским исполнителем после
просмотра итоговых файлов:

```text
python tools/publish_v127_release.py --publish
```

Она не делает force push, не заменяет существующий чужой тег/ассет и не
перенумеровывает объекты. Сначала проверяет принятую поставку и неизменность
кода, публикует обычную ветку/неизменяемый тег, создаёт draft GitHub Release и
загружает файлы потоками. Повторный запуск восстанавливает уже законченные
загрузки по имени/размеру/SHA; повреждённый или конфликтующий ассет останавливает
публикацию для разбора. После загрузки draft открывается, каждый публичный
ассет скачивается потоком и сверяется по SHA. Результат сохраняется в
`build/v127-release-publication.json`.

Учётные данные берутся из Git credential helper только в память процесса.
Токен не записывается в файлы, командную строку, отчёт или URL; публичное
скачивание выполняется без Authorization. API используются по
[документации GitHub](https://docs.github.com/en/rest/releases/assets).
