# Клиент: повторный разбор и копирование multipart-моделей

Предварительный настоящий клиент с JAR SHA256 `34c2f13cc2e3ca070d628e04ac438b6e1f167f960169789605b921cb43ea7065` не дошёл до мира: загрузка ресурсов началась в 03:40:17, в 03:47:57 зарегистрирован `OutOfMemoryError: Java heap space` при heap 4 GiB. Снимок потока в 03:42:24 показывает 125 546,88 ms CPU у Worker-Main-6 на повторном `SimpleMultipartModelSelector.getPredicate` / `Splitter.splitToList`. Снимок в 03:47:07 показывает 378 109,38 ms CPU того же потока на `ModelLoader.BakerImpl` / `MultipartUnbakedModel.bake`. Это реальные диагностические данные неудачного клиента; серверный нативный PASS и его измерения памяти не заменяют клиентский запуск.

Первичные доказательства сохранены в `client-memory-evidence/`: два полных дампа потоков, настоящий журнал клиента и `primary-evidence.json` с хешами и разбором закреплённых классов Minecraft 1.20.1/Yarn build10 и официального Fabric Model Loading API 1.0.4. Разбор классов не запускал Java: байткод прочитан Python из уже существующего локального кеша. Дампы потоков получены родительским заданием у настоящего запущенного клиента. Дополнительный `client-predicate-readonly-proof.json` хранит подписи и ссылки вызовов пути предикатов.

В 256 собственных multipart JSON обнаружены 24 904 компонента и 92 472 конечных условия. Наибольшая группа — `source_assembly_brick_wall`: 6 645 компонентов и 26 577 условий. Её публичная область содержит 30 720 состояний, поэтому обычный полный обход требует 204 134 400 обращений к предикатам компонентов. Это прямой подсчёт структуры, а не измерение байт heap. Все 256 JSON используют одиночные применения моделей; составных массивов случайных весов нет. При этом логика сохраняет и более общий случай различных фактически запечённых дочерних объектов.

На checkpoint `7be6a98655bb01801350db7154877921124ca3a9` добавлены две ограниченные клиентские оптимизации:

- Каждый разобранный `MultipartModelComponent` хранит одну неизменяемую пару «точный StateManager по identity → скомпилированный Predicate». Чужие и ванильные менеджеры выполняют прежний код. Другая собственная область заменяет пару. Объекты живут только вместе с разобранным графом текущей перезагрузки ресурсов; нет кеша результатов по отдельным состояниям, миру или координатам. Redirect оборачивает единственный вызов компиляции, не создавая CallbackInfo на каждом горячем попадании.
- Каждый разобранный `MultipartUnbakedModel` хранит один фактически запечённый основной граф. Проверка выполняется только после всех настоящих дочерних bake-вызовов, в последнем `Builder.build`. Для повторного использования должны точно совпасть порядок, identity каждого предиката и дочерней BakedModel, identity поворота и uvLock. При несовпадении выполняется прежний native build. Sprite getter, current ID, дочерние вызовы и внешние Fabric BeforeBake/AfterBake callbacks продолжают проходить обычный путь.

У разделённого собственного основного графа прежний нетредобезопасный кеш BitSet заменяется ленивой ConcurrentHashMap до публикации модели. Горячее чтение не сканирует всю область состояний. Холодная запись проверяет точную принадлежность `StateManager.getStates().contains(state)`; чужие и вручную созданные незарегистрированные состояния не удерживаются. Максимум записей ограничен самой неизменяемой областью зарегистрированных состояний. Ванильные и чужие графы сохраняют прежний кеш. Глобальных карт моделей, ссылок на старые перезагрузки и собственных наборов всех состояний не создаётся.

Публичные свойства, числовые и registry ID, геометрия, UV, материалы, BASE/ALT, авторские PNG и поведение V12 этим кодом не меняются. Независимый разбор первичного байткода и чтение реализации подтверждают границы вмешательства. Это статический **PASS** понимания механизма; динамический результат нового клиента пока **NOT_RUN**.

Отдельные opt-in классы нативного QA не входят в производственный JAR. `NativeMultipartPredicateQa` сравнивает независимые нативные AND/OR, pipe и negation по реальным собственным областям, identity повторных вызовов, разные менеджеры, новую reload-инстанцию и ванильный обход без кеша. `NativeMultipartCoreQa` проверяет настоящие native bake-вызовы, identity детей, порядок, поворот и UV, model header, обычные и разделённые кеши, current-ID образцы дочерних вызовов, 2 048 сравнений quads четырьмя рабочими потоками и отсутствие удержания чужих/незарегистрированных состояний. После открытия мира отдельный наблюдатель требует равных настоящих BeforeBake/AfterBake счётчиков и совпадающих крайних top-level ID. Оба proof связаны с SHA256 конкретного производственного JAR.

Ожидаемые файлы нового фактического запуска — `v127-native-client-predicate-proof.json`, `v127-native-client-core-proof.json` и прежний отчёт 17 игровых кадров. Успешная компиляция не считается их выполнением. Итоговый статус и измерение клиентской RAM должны быть добавлены после родительского сериализованного прогона; на момент этого документа они не заявляются.
