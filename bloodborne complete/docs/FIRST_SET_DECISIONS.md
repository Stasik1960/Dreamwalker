# Первый набор: исходные доказательства и следующие решения

Статус: исходный набор для прототипов, **не готовый каталог и не преобразование всего мира**. Название итогового мода задаётся пользователем: `dreamwalker-bb-fabric-1.20.1`. Цифровые ID не закреплены. Все координаты ниже относятся к исходному Overworld 1.18.2. Bounds указаны в model units, 16 units = 1 блок; это визуальная геометрия, не сплошная коллизия или маска установки.

Источники: `bbmc_v15_resource (1).zip` + подтверждённый Mojang client 1.18.2, исходный `bbmc_v16_map (1).zip`. Точные JSON, SHA, selectors и transforms: [RESOURCE_AUDIT_MODELS.json](../reports/RESOURCE_AUDIT_MODELS.json), [RESOURCE_AUDIT_WORLD_JOIN.json](../reports/RESOURCE_AUDIT_WORLD_JOIN.json). Реальные соседние клетки и два дерева: [FIRST_SET_SOURCE_EVIDENCE.json](../reports/FIRST_SET_SOURCE_EVIDENCE.json). Ниже обозначены именно кандидаты самостоятельных объектов; числа исходных клеток не являются числом объектов.

## Деревья, которые действительно найдены

В полном resource inventory **18** model records используют `tree_1/tree_2/tree_3` atlases; atlas сам по себе ещё не классифицирует объект: `tree_1` содержит также архитектурные фрагменты. Полный state join даёт **11 055** клеток, выбирающих эти модели, считая состояние один раз независимо от random alternatives. Это частота носителей, **не число деревьев**. Точные UV, file SHA и все модели перечислены в `FIRST_SET_SOURCE_EVIDENCE.json`; исходные PNG побайтно скопированы в `reports/FIRST_SET_SOURCE_IMAGES/`.

Два локальных примера имеют центры x/z `[-16,-504]` и `[-14,-500]`; все следующие позиции проверены непосредственно в ZIP:

| Y | Центральная клетка | Четыре боковые клетки относительно центра |
|---|---|---|
| 119, 122 | `melon`, продолжение ствола | Нет боковых членов в выбранном шаблоне |
| 125 | `orange_wool` | `jungle_log` в z-3 axis=x и x+3 axis=z; `oak_log` в z+3 axis=x и x-3 axis=z |
| 128 | `magenta_wool` | Аналогично `acacia_log` / `spruce_log` |
| 131 | `light_blue_wool` | Аналогично `dark_oak_log` / `birch_log`; birch имеет два source random alternatives, выбранных из первоначальной позиции |
| 134 | `cyan_wool`, верхняя часть | Нет боковых членов в выбранном шаблоне |

У каждого примера **18 проверенных source cells**; нижняя опора непосредственно в Y=118 — `grass_block[snowy=false]`. Объединённые bounds выбранных элементов в world coordinates: первый `[-20,118,-508]..[-11,136,-499]`, второй `[-18,118,-504]..[-9,136,-495]`. Точки ствола и ветвей разнесены на 3 блока; это сложенная структура с картинкой дерева, не один log block. Выбранные variants, geometry SHA и исходные pivots записаны по каждому члену.

Клетки двух наборов не совпадают, но видимые bounds пересекаются. Внутри первого широкого AABB находятся **61** занятая клетка вне его 18 членов, во втором — **114**; среди них грунт и части другого дерева. Маска из заполненного AABB разрушит соседние объекты. Сначала нужна раздельная геометрия ствола/ветвей и явный механизм сосуществования service cells в местах реального пересечения. Локальный шаблон не разрешает автоматически назначить все 11 055 клеток этим двум новым типам деревьев.

RP scope остаётся отдельным: `bloodborne:tree1=19`, `tree2=27`, `tree3=13` (**59 RP entities**). Их UUID, позиция, rotation, scale и сохранённые данные сохраняются; превращать их в блоки при миграции архитектурных деревьев не требуется. Ранее `ARCHITECTURE_TREE_NOT_YET_IDENTIFIED` в предварительном отчёте означает состояние того раннего этапа; подтверждённые локальные наборы выше его уточняют.

## Поддержки и пересечения первого набора

- Дверь east `[-58,76,-113]`: source `barrier` в y-1/y+1 и z±1. Эти клетки имеют реальное назначение в карте; смена нового pivot, ownership и удаление старых barriers требуют конкретного manifest. В north примере источник `[−93,59,−212]` пуст между двумя door carriers, а рядом deepslate/stone; геометрический объём двери всё равно выходит за носитель.
- `door_1` на `spruce_stairs top straight`, например `[-307,70,-221]`, — отдельный фасадный кандидат с 7 глубокими элементами, bounds `[-2,-10,-3.5]..[18,32,19.5]`. Имя не доказывает подвижную дверь. Соседние brick/blackstone walls нельзя включать в исчезающее обрамление.
- У `wood_window` кирпичи в z-1, `warped_fence` в x-1 и z+1, повторяющиеся окна в y+1/y+2. Более широкая service mask должна сохранить владельцев стен/оград и соседних окон. `window_01` тоже расположен рядом с кирпичной стеной, без права её удалить.
- У модульной стенки `[154,58,-976]` снизу ещё одна wall cell, сбоку `calcite`, сверху `prismarine_stairs`. Геометрия post/low side умещается в свою клетку; превращать эту ограду в spire/pillar или копировать vanilla collision 1.5 блока не следует без самостоятельного правила коллизии.
- Ladder carrier/support и climbing cell — две исходные роли, не два готовых независимых объекта. Верхние площадки пересекаются с поддержками diorite/glass; самостоятельная уборка частей должна убрать только собственные части.

## Что можно выполнить автономно сейчас

1. Сохранить source resource closure каждого выбранного объекта в собственном namespace; зафиксировать исходные ordered variants/UV/element transforms. Отрисовать точный закрытый набор, включая double faces и пересечения с существующими стенами. Это не требует окончательных цифровых ID.
2. Подготовить функциональную door proposal: фиксированное верхнее обрамление `aca_door_2`, отдельно выделенные две door leaves внутри рисунка `aca_door_1`, hinges у боковых краёв. Разделение исходной одной face на фиксированные и подвижные UV участки должно сохранять закрытый рисунок без перерисовки. Конкретные moving UV bounds/pivots надо сделать обозримыми и проверить; источник не задаёт готовую открытую позу.
3. Подготовить window proposal с неизменным центральным элементом и подвижными боковыми элементами на authored pivots. Показать исходную позу и предложенные пределы поворота; проверить click из обоих направлений, frame, соседей и физический проход.
4. Построить из одного подтверждённого 18-cell дерева отдельный prototype с root/parts/ownership и сохранёнными source variants. Испытать все повороты, дальние части, перенос, опору и однократное удаление. После изолированного случая испытать два реально пересекающихся source дерева. Никакой автоматической очистки их широких AABB.
5. Реализовать independent wall module с собственными post/sides, соединением с новым семейством, raycast/outline и collision по выбранным собственным элементам. Проверить рядом обычную vanilla стену, чтобы vanilla внешний вид сохранялся.
6. Прогнать общие placement/rollback/part cleanup/neighbor update/server-client/RP save checks для всего первого набора. Затем предоставить пользователю конкретный игровой набор для обязательной визуальной и игровой приёмки из TASK.md. До неё массовая генерация каталога и преобразование исходной карты не запускаются.

## Реально не закреплено

Source не содержит полной карты «подвижная створка против фиксированного рисунка» у `aca_door_1`, готовых open poses двери/окна, collision/placement masks и окончательных правил глобального членства деревьев. Это не препятствует подготовке обозримых предложений и локальным прототипам; оно препятствует объявлению этих предложений доказанным исходным поведением и автоматической массовой миграции. Все спорные пересечения необходимо фиксировать с координатами и выбранным решением, без удаления посторонних клеток.

Полная высота карты отдельно подтверждена [HEIGHT_AUDIT.json](../reports/HEIGHT_AUDIT.json): 35 890 terrain chunks, занятые Y=-64..319; source `gray_terracotta` в `[140,319,-510]` имеет видимую геометрию до Y=321. Обычный source и target Overworld допускает клетки только до Y=319. **Галерея NOT_GENERATED**: после freeze ID её размещение выше города требует отдельной явно заданной конфигурации высоты/измерения галереи; основной мир автоматически не расширяется.
