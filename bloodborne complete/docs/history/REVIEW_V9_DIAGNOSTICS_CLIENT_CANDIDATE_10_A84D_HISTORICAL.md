# Клиентская диагностика V9

Подробная запись выключена по умолчанию. Для управления нужны права оператора уровня2. Ошибки собственных моделей и текстур сохраняются в ограниченном журнале независимо от записи; повторные сообщения имеют счётчик. Обычный отказ установки из-за физического пересечения — событие, а не аварийная ошибка.

```text
/bb diagnostics start
/bb diagnostics start 60
/bb diagnostics start 60 id 90010
/bb diagnostics start 60 object
/bb diagnostics start 60 area 16
/bb diagnostics mark стекло не видно с обратной стороны
/bb diagnostics snapshot невидим
/bb debug
/bb diagnostics status
/bb diagnostics stop
/bb diagnostics export
```

`start` без числа записывает60 секунд и автоматически прекращает запись. `object` выбирает объект под прицелом; `area` задаёт радиус вокруг игрока. Действие инструмента «диагностический снимок» сохраняет сведения о выбранном объекте без изменения объекта. Пометка снимка доступна через `snapshot <текст>`.

Серверный ZIP записывается в `dreamwalker-diagnostics` относительно рабочего каталога сервера; команда выводит абсолютный путь. Клиент автоматически сохраняет свой ZIP после остановки или истечения сеанса в `<каталог игры>/diagnostics/dreamwalker-client-<UUID>.zip`. Его журнал ошибок находится в `<каталог игры>/logs/dreamwalker-client-errors.jsonl`. Клиентский и серверный ZIP связаны UUID сеанса. Серверный экспорт содержит принятые клиентские пакеты, но локальный ZIP удалённого клиента недоступен серверу автоматически.

Для обычной установки сервер передаёт реальный предмет, принятый тип, корень/UUID экземпляра и номер операции. Клиентская запись фактически выбранной рендерером модели прикладывает это подтверждение. Предмет в руке в момент наблюдения указан отдельно: он мог измениться после установки. Для ранее загруженных объектов без наблюдавшейся установки цепочка явно содержит `ITEM_NOT_OBSERVED_IN_ACTIVE_SESSION`.

Интервалы кадров снимаются на `RenderSystem.flipFrame`; они включают VSync, ожидание и работу планировщика. Среднее, медиана, p95/p99, количество сохранённых и отброшенных измерений относятся к указанному окну. Квантили FPS вычисляются по обратным положительным интервалам: высокий FPS соответствует малому времени кадра, а не обратному p95 времени кадра. Замеры собственного рендера CPU и фактического времени потока CPU не являются временем GPU. GPU-время и точная доля нагрузки объекта по FPS не измеряются. Настройки Iris, если мод загружен и его публичный API доступен, считываются один раз в начале сеанса: версия, включение, имя пакета, fallback и класс pipeline. Отсутствие или несовместимость API указаны явно.

Настоящие паузы GC наблюдаются через JFR `jdk.GCPhasePause`. Уведомления о длительности цикла GC и агрегатное время MXBean записываются отдельно и не называются паузами STW. Встроенный сервер и клиент могут иметь один PID: их память и GC относятся к общему процессу и не суммируются. Сетевые счётчики охватывают явно инструментированные каналы; полный трафик всех модов и связанный vanilla-трафик не заявляются измеренными.

Буферы событий, ошибок, моделей, выборок и пакетов ограничены; пакеты отправляются раз в секунду. Выборка CPU выполняется с ограниченной частотой. Клиентская очередь файловой записи имеет ёмкость4, экспорт создаёт новый файл и сохраняет четыре последних собственных ZIP. Ошибка записи отчёта не меняет мир. Число клиентских сущностей сканируется до20000, с явным признаком усечения; чанки ради метрик не загружаются принудительно.

Маркер проверки в изолированной копии сцены дополнительно включает реальные окна OFF→ON→OFF при неизменной камере и восстановленном предмете. Временное стекло90010 устанавливается обычным клиентским взаимодействием с существующим полом, требует серверного подтверждения и выбора модели настоящим BER, затем удаляется обычным разрушением. Проверка сверяет восстановление точных исходных ячеек и пола, сохранение мира, автоматическое прекращение и оба ZIP. Сырые интервалы кадра/CPU сохраняются в QA-отчёте; различия между окнами не объявляются точной причинной стоимостью диагностики.

Текущий JAR с SHA256 `a84d202c4f404ba48b6219e864f915f9160b0e0153b1b5a708d731f9ffd6d1a0` прошёл [независимую фактическую проверку](../reports/REVIEW_V9_DIAGNOSTICS_INDEPENDENT_RELEASE7.json): чистый серверный OFF/ON/default60, клиентский OFF→ON→OFF, обычная установка90010 с подтверждением сервера и настоящего рендерера, полное удаление временного владельца, истечение сеанса и оба ZIP. Повторный вход в реально сохранённый мир с новой записью прошёл в [client reenter8](../reports/CLIENT_MINIMAL_REENTER_V9_RELEASE8.json). Первоначальный режим присоединившегося игрока был Survival; изолированный QA явно включил Creative до всех трёх окон и восстановил Survival после них. Обычные игровые проверки Survival выполнены отдельно. Полный клиент109 модов с Kappa5.2 release7 при heap4 ГБ достиг99% heap и длительных GC; нормального выхода не было, этот FAIL сохранён. Свежий release8 при heap6 ГБ остаётся ожидающим. Это разные условия heap; повтор не доказывает работоспособность полной сборки при4 ГБ. Ручное визуальное одобрение и готовность полного каталога не заявляются.
