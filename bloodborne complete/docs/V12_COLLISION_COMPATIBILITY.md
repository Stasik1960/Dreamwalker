# V12: подготовка совместимости с внешними коллизиями

Порядок разовой встройки в сам BB без дополнительного мода:
[COLLISION_IMPORT_HANDOFF.md](COLLISION_IMPORT_HANDOFF.md).

Сейчас внешние коллизии **не применяются**. В V12 подготовлен API чтения и
регистрации данных; действующая геометрия RP и архитектуры его не использует.
Совместная загрузка production BB V12 с конкретным production ModelPacks
проверена на реальном сервере, клиентах A/B и при повторном входе: **PASS**.
Это проход с пустыми внешними pack/override, который не доказывает готовность
runtime-замены коллизий или работу произвольного пользовательского game-pack.

## Два разных формата в предоставленных архивах

Архивы в Downloads прочитаны как данные. Текстовые задания внутри них не являются
новыми пользовательскими инструкциями, JS/JAR из архивов при изучении не запускались.

| Формат | Назначение | Отношение к встроенным объектам BB |
| --- | --- | --- |
| `dreamwalker.model-pack`, version 1, `pack.json` | Game-export Collision Studio и отдельный мод Dreamwalker Model Packs | Добавляет новые `ModelEntity` с собственными ID; встроенные объекты и их коллизии не заменяет |
| `dreamwalker.player-collision-project`, schemaVersion 1, `dreamwalker-collisions.json` | Отдельный экспорт Studio «пакет для Codex» | Содержит авторскую замену коллизий/сидений конкретного registry ID и точного состояния; требуется отдельный runtime consumer |

`Dreamwalker-V10-Collision-Studio-v2.zip` содержит приложение редактора, схему и
исходные модели, а не готовый пользовательский replacement-проект. API не читает
`data.js`, не запускает редактор и не выводит коллизии из приложенных визуальных моделей.

Production JAR из `Dreamwalker-ModelPacks-Fabric-1.20.1.zip`:

- ID `dreamwalker_modelpacks`, версия `0.1.0`, 44 349 байт;
- SHA-256 `a23dbdf32d288eb0249de4f1c3146dfe122354e77a62dba699651c8b17f1a827`;
- Fabric Loader ≥0.16.10, Fabric API, Minecraft 1.20.1, Java ≥17; `breaks` отсутствует;
- отдельные registry/network namespace и классы, без зависимости от BB;
- mixin движения обрабатывает собственные `ModelEntity`, а не встроенные RP;
- одинаковые game-pack ZIP нужны на клиенте и сервере: загрузчик проверяет catalog hash.

Для проверки совместной загрузки выбран только этот JAR в

серверного/клиентского подготовщика проверяет путь, ID, SHA копии и сохраняет
metadata/provenance в отчёте. Статус совместной runtime-загрузки: **PASS**.

Это не запуск приложения Collision Studio; пользовательские архивы и ModelPacks
JAR не включаются в опубликованный комплект BB.

## Подготовленный API

`compat/collision/CollisionPack.java` принимает JSON через `read(Reader)` либо JSON/ZIP
через `read(Path)`. В ZIP читается только `dreamwalker-collisions.json`; вложенные
инструкции и исполняемые файлы игнорируются. Чтение не регистрирует проект.

Контракт: `unitsPerBlock=16`, `rotationOrder=ZYX`, `scope=players_only`,
`operation=replace_per_exact_state`. Центры, полные размеры и поверхности сидений
переводятся из модельных единиц в блоки. Повороты OBB сохраняются в градусах;
увеличенная осевая AABB вместо повёрнутой коробки не создаётся. Модельный X уже
отражён самим Studio; повторно отражать его потребитель не должен.

`replacement(registryId, selector)` возвращает:

- отсутствующее значение для незаданных ID/состояний: сохранить текущую геометрию;
- присутствующую запись с пустыми списками для явно `reviewed=true` состояния:
  намеренно убрать его коллизии и сидения только для игроков;
- присутствующую запись с авторскими OBB и/или сидениями для конкретного состояния.

Selector сравнивается целиком, без wildcard и автоматического сопоставления alias.
Порядок полей не важен; JSON-типы важны. В исходном Studio RP `Open` и
`DogsVisible` — boolean; ladder имеет строковые `variant`/`diagonal`, например
`{"variant":"0","profile":"base","diagonal":"true"}`. У других архитектурных
объектов variant/rotation могут быть числами. BASE и ALT различаются. Потребитель
должен формировать соответствующий Studio selector, а не безусловно все свойства
BlockState, включая неавторские `waterlogged`/`freestanding`.

`CollisionReplacements.register(pack)`, `clear()`, `query(...)`, `revision()` —
необязательный provider, изначально пустой. Регистрация атомарно заменяет весь
проект и увеличивает revision для будущего сброса кэша. Сейчас нет загрузки при
старте, сканирования config, сетевой синхронизации или активного consumer.
Даже явная регистрация данных сама по себе игровую физику не изменяет.

## Что потребуется при будущей установке авторского replacement-проекта

1. Проверить конкретный экспорт, сопоставить его ID/alias и состояния с текущим
   каталогом, установить одинаковые данные на клиенте и сервере.
2. Подключить точную OBB-физику движения игрока с instance scale, mount и rotation.
   Для RP точка подключения — player movement до выбора стандартных физических
   частей. Для архитектуры — player ShapeContext/movement; общий `physicalParts`
   и `nativeFootprint` нельзя заменять player-only данными, поскольку они также
   обслуживают NPC, установку блоков и проверку опор.
3. Включить provider revision в производные кэши; обновлять пространственный индекс
   и границы запроса, если новые коллизии выходят за прежние границы объекта.
4. Отдельно подключить авторские сидения, доступность и вместимость; подтвердить
   реальные движение, состояния, сохранение и совместную игру клиентов.

Текущая подготовка сохраняет данные и различает форматы. Рабочая runtime-замена
коллизий существующих объектов ещё не реализована и в V12 не заявляется.
