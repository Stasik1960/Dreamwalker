# Проверка инструмента 90009

Это сценарии приёмки исправления на базе V10, а не объявление готовности или новой принятой версии. Допустимые результаты: **Проверено в игре**, **Проверена внутренняя логика**, **Не проверено**, **Ошибка**. Запуск настоящего клиента скриптом обозначается как автоматическая игровая проверка; проверка человеком не подразумевается.

Для каждой проверки записывают точный новый combined JAR и SHA256, Loader/Fabric API/GeckoLib/Java, одиночный или отдельный сервер, UUID выбранного экземпляра, действие, ответ сервера, состояние до/после и доказательство. Успех старого отчёта V10 не переносится на новую сборку. Внутренний вызов `applyBlock`, setter или NBT loader подтверждает соответствующий участок; он не подтверждает мышь, окно, сеть, модель или первый вход.

Фактические результаты и привязка сборки находятся в `reports/TOOL_FIX_TEST_MATRIX.json`. Пока результат в строке не заполнен с доказательством, её статус — «Не проверено». Уровни одной проверки учитываются отдельно: автоматическая логика / отдельный сервер / настоящий клиент / точный выдаваемый JAR без QA-мода.

## Среда и стенд

Minecraft 1.20.1, Java 17, Fabric Loader 0.16.10+, Fabric API 0.92.9+1.20.1+, GeckoLib 4.4.9 (<5). Исходный ресурс-пак и Kappa BB отсутствуют. Клиентский набор других модов пользователя не предоставлен, проверка его конфликтов остаётся самостоятельным сценарием.

Стенд воспроизводится командой:

```sh
python tools/prepare_tool_fix_fixture.py --source /path/to/Review-v10-scene.zip --output build/tool-fix-review-fixture
```

Исходный архив не меняется, новый каталог нельзя заменить повторным запуском. Распаковать новую папку `Tool-fix-review-scene` в `saves`. Creative, читы и предмет 90009 настроены до первого одиночного входа. Vanilla datapack дополнительно выдаёт 90009 и Creative каждому новому игроку, в том числе на отдельном сервере. Для администраторских событий на отдельном сервере оператору нужен уровень 4 (`op-permission-level=4` и `op <имя>` в консоли). Datapack относится только к стенду, не поставляется как функция основного мода.

## Безвредные события

Создать счётчик один раз командой `/scoreboard objectives add dw_tool_test dummy`. После открытия использовать две последовательные строки:

```text
scoreboard players add opened dw_tool_test 1
tellraw @a {"text":"Открытие {id}; UUID {uuid}","color":"green"}
```

После закрытия: `scoreboard players add closed dw_tool_test 1`. Ошибочная строка: `dw_this_command_does_not_exist`. Снимать значения `/scoreboard players get opened dw_tool_test` и `closed` до/после; неподходящая команда не должна очищать списки. Не использовать массовый `kill` сущностей: двери/рычаги/фонари тоже сущности.

## Автоматические механизмы

Новая `ToolMigrationGameTests` проверяет все 18 численных режимов V10, отсутствие мутации входного NBT, типизированные данные/количество/идемпотентность, native `PlayerInventory.readNbt`, `ChestBlockEntity.readNbt`, `ItemEntity.readNbt`, единственный инструмент Creative и независимость/сохранение собак всех трёх типов. `ToolGeometryGameTests` проверяет серверный адаптер прямого/обратного поворота и монтажа всех трёх стекол при взгляде в другую сторону. `ToolServerPipelineGameTests` проходит фактическую серверную обработку запросов/сессий с тестовым соединением: выбор лучом, два шага вверх, обратный вниз, поворот без прицеливания, сохранение UUID после открытия меню, отмену/повтор запроса, конфликт двух игроков и предел истории 20. Успех этих тестов помечает только внутреннюю логику.

Существующие `ArchitectureVerticalMountGameTests`, `GlazingMountGameTests`, `SourceLadderGameTests`, `RpV10EditingGameTests`, `MechanismLinksGameTests`, `MechanismRulesGameTests`, `ObjectPolicyGameTests`, `LampV10GameTests`, `DwDiagnosticsGameTests` используются как регрессии затронутого кода. Их старые результаты недостаточны; нужны новые XML/логи с идентификатором сборки. QA/game-test entrypoints не требуются пользователю или обычному стенду.
